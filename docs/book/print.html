1. Background

prikk is a verifiability-focused version-control system built around block-oriented patch theory: an offline, single-repository CLI with Ed25519 author and maintainer signatures, sealed immutable blocks, offline verify, and artifact-based exchange. Around it an ecosystem follows one pattern: each companion carries a weight prikk refuses, so prikk stays small. planeter carries the hosting weight (the forge). wiki-commons is the owner’s open guideline suite for wiki engines: a pattern language and portable conventions so that knowledge outlives the software it was written in.

The owner’s question that opened this project: what becomes possible when a wiki’s storage is a patch-theoretic VCS, and could such a wiki foster an inclusive, open community culture? The answer worked out in the requirements analysis is that the interesting move is not “store wiki data in a VCS” but model the knowledge community itself as a patch system: knowledge is a set of revisable claims; every change is a proposal; disagreement can coexist as branches; forks are legitimate; governance is explicit and itself versioned. The same analysis recorded why people give up on wikis: an edit reverted without a word, opaque local rules, the pressure to be perfect, unfamiliar markup, formalism, information chaos, the burden of maintenance landing on whoever wrote the page, and no recognition. inklkunn is designed against that list.

planeter’s open question OQ-4 asks whether wikis belong in the forge’s v1. inklkunn is the answer the owner chose: a wiki engine that joins the forge as a module. inklkunn is Norwegian, “inclusive” + “knowledge”.

2. Goal

Be a wiki engine where participation starts with a proposal, whose history is prikk’s, usable on its own and embedded in planeter. A reader should be able to read, ask, suggest, add a source and propose a change without knowing Markdown, Git, or the community’s power structure; a reviewer should see exactly what a proposal changes and why; a maintainer should accept it with one action; and anyone holding the repository should be able to verify its history offline with prikk alone.

The commitments that make it this project (the owner’s rulings of 2026-10-24):

  1. Wiki-first, claims layered in (DR-1). Pages are the stored artifact; claims, evidence, views and provenance arrive as explicit objects above them, named from the start, load-bearing from the third milestone.
  2. An independent service that planeter embeds (DR-2). inklkunn owns its repositories, keys and threat model; planeter integrates it at the identity, authorization and presentation level and may host the same repositories read-only. planeter stays keyless.
  3. Built above prikk, over its CLI (DR-3). A sandboxed, version-pinned subprocess behind a storage trait; never prikk’s crates; never weight pushed into prikk.
  4. The wiki service signs as itself (DR-4). It holds one author and one maintainer key per wiki, records the human behind each change in the signed message and in its own records, and labels every signature honestly. Per-account and client-side keys are later opt-ins.
  5. A wiki repository is a Portable Wiki Bundle (DR-5). Pages are Markdown files in the Portable Wiki Markdown profile with frontmatter; export is a copy and import is a commit; prikk’s file-level patches fit page-level edits.
  6. Inclusive by construction. A message catalog in English and Japanese (DR-7), plain words, WCAG 2.2 AA checks that fail the build, and no JavaScript required to read or to propose.
  7. Clean, safe, secure and robust before rich, and less is more (the owner’s standing design philosophy). Real-time co-editing is deferred (DR-6); the default content license for public wikis is CC BY-SA 4.0 (DR-8).

3. What “done” means

1.0 is the usable wiki, complete: read, propose and accept, the knowledge layer (claims, evidence, views, provenance), explicit governance and moderation, interchange and an API, the planeter module, hardened and backup-tested, with versioned conformance claims against wiki-commons. Promotion to 1.0 is an explicit owner decision; green gates and feature completeness are necessary, not sufficient. Until then everything is 0.x and honest about what is not there.

Each milestone is usable on its own: M1 read a wiki → M2 propose and accept → M3 claims and views → M4 governance → M5 interchange and API, with the planeter module as a joint RFC alongside (ROADMAP.md §3).

4. What inklkunn will not do (the non-goals, as firm as the goals)

Not a code forge or a prikk host (planeter is); not a change to prikk (a needed capability is a named dependency and a letter, never a prikk patch inklkunn writes); not a truth oracle (provenance is not truth; no universal truth or reputation score); not a real-time editor or a block database in v1; not federation, portable identity or AI authority in v1 (AI assistance, when it comes, is advisory and labelled); not a second source of truth for history and never a rewriter of it; not a lock-in (export, archive and independent verification are requirements); not a general content-management system, and never an executor of content-provided code. Requirements NG-1 … NG-9.

5. Constraints inklkunn accepts

  • prikk’s model binds the write path. Every commit is author-signed, every seal maintainer-signed; prikk detects conflicts and never resolves them; same-file text transforms are deferred in prikk, so content-level merge is inklkunn’s; prikk has no network, no object deletion and no ref deletion.
  • prikk moves fast and its JSON is pre-1.0. inklkunn pins a floor (0.54 for M1) and re-baselines at each prikk release; schema drift is a refusal, not a guess.
  • planeter has no module mechanism today. The module is a joint RFC on both sides; until it exists inklkunn ships standalone.
  • Linux first for the server (the sandbox for the prikk subprocess is bubblewrap, as in planeter); prikk itself runs on Linux, macOS and Windows. The standalone binary makes no claim it cannot run.
  • The ecosystem’s engineering rules: Rust 2024, a declared and tested minimum compiler, forbid(unsafe_code), a measured and allow-listed dependency tree, --locked everywhere, tests apart from implementation files, English for all documentation and code, bare X.Y.Z release tags.
  • Security is release-gating. A release touching identity, signing, the prikk boundary, rendering or inbound content updates the threat model; the others re-verify it.

6. Who decides what

  • The owner (nabbisen) decides direction, priorities, scope, milestones, the owner-only questions (requirements §16), every tag, publish and release, letters to the prikk and planeter teams, and the 1.0 promotion.
  • The architect (a high-capability AI agent) writes requirements, design, RFCs, handoffs, the schedule and the records; reviews every implementation; drafts upstream letters; recommends releases.
  • The dev team (a mid-capability AI agent) implements from handoffs and returns evidence.

1. Purpose (PU-…)

  • PU-1 — Participation starts with a proposal. Every change to a wiki’s content is a proposal that is read, discussed and accepted. A newcomer’s first act can be a question or a suggestion, never an edit that overwrites, and the system never asks a reader to understand the machinery beneath it (main transcript §3, §8; principle 1).
  • PU-2 — Make provenance, disagreement and governance visible. Every sentence and every claim can be traced to who proposed it, what supports it, what challenges it, and who adopted it under which rule. Competing views coexist and are shown as such. The rules for changing knowledge are themselves visible and revisable (principles 2–5). Provenance is not truth, and the system never claims it is.
  • PU-3 — Build above prikk, over its CLI, pushing no weight down (DR-3; prikk RFC 145). prikk stays the sole source of truth for history and verification; a wiki repository stays an ordinary prikk repository that anyone can verify offline with prikk alone.
  • PU-4 — Be an independent service that planeter embeds (DR-2) without weakening planeter’s guarantees, and that works on its own.
  • PU-5 — Be inclusive by construction. Accessible (WCAG 2.2 AA, ATAG 2.0), multilingual, written in plain words, usable without JavaScript, respectful by default; a low barrier to legitimate participation and safeguards against abuse (register item 19; C-15).
  • PU-6 — Clean, safe, secure and robust before rich; less is more. The default view shows little and depth is one step away. Nothing ships half-safe (the owner’s standing design philosophy).
  • PU-7 — Portable: knowledge outlives the software (wiki-commons PR-16). The repository is a Portable Wiki Bundle and a prikk repository; export is a copy and import is a commit; conformance claims are honest and versioned.

2. Non-goals (NG-…) — stated as firmly as the goals

  • NG-1 — Not a code forge and not a prikk host. planeter is. inklkunn hosts wikis, not software repositories; it does not clone, push, run CI or publish packages.
  • NG-2 — Not a change to prikk. No new prikk command, format or protocol. A needed capability is a named dependency (§15) and a letter through the owner, never a prikk patch inklkunn writes.
  • NG-3 — Not a truth oracle. No field, score or label asserts truth; there is no universal numeric truth or reputation value; “adopted in the default view” is a community decision with a visible history, never a claim of fact (register items 2, 9, 10; C-12).
  • NG-4 — Not a real-time editor and not a block database in v1. Real-time co-editing is deferred (DR-6). Pages are documents with block identifiers, not a tree of typed blocks with live queries (register item 11; DR-1).
  • NG-5 — Not the frontier by default. No federation, no portable identity, no AI with authority in v1. AI assistance, if ever added, is advisory, labelled, and attributed to the human who accepted it (register items 16, 17; C-13; wiki-commons AUTH-14).
  • NG-6 — Not a second source of truth for history, and never a rewriter of it. Service records hold review state and attribution; history is prikk’s. Removal is suppression on the view plus a documented repository-level procedure, never a silent rewrite (register item 14; C-14).
  • NG-7 — Not a lock-in. The bundle export, the prikk archive export, independent verification by any prikk, and the export of the service’s own records are requirements.
  • NG-8 — Not a content-management system and not a macro engine. No content-provided code ever executes; declared extensions degrade to readable text (wiki-commons EXT-3, SEC-6).
  • NG-9 — Not a multi-tenant commercial platform. One operator runs one inklkunn with one or more wikis; billing and tenancy beyond per-wiki authorization are out of scope.

3.2 The participation ladder

The main transcript’s ladder, Visitor → Observer → Questioner → Contributor → Reviewer → Maintainer, is the product’s model of growth: observation is a legitimate first step, and each rung adds one capability (read, follow, ask, propose, review, accept). The ladder is per wiki and is policy data (GV-2), never an opaque score.

3.3 Core use cases

  • US-1 Read a page; follow links including links to pages that do not exist yet; see what links here; see when the page last changed and by whom; see whether the repository verifies.
  • US-2 Ask a question about a page in its discussion without editing anything.
  • US-3 Propose a change to a page or to one section of it: a fix, new text, a source added, a wording change, with a reason; preview it; see what it changes; submit it; receive a URL for the proposal.
  • US-4 Follow a proposal: see what it changes, read the discussion, see who reviewed it and the decision; if declined, be told respectfully, with the reason and a next step.
  • US-5 Review a proposal: read the change page by page and block by block, comment inline, approve or request changes.
  • US-6 Accept a proposal in one action: the page updates, the change is signed into the history, the proposer and the acceptor are credited.
  • US-7 Undo an accepted change: propose a rollback, which goes through the same loop.
  • US-8 Ask “why is this here?”: trace a sentence to its proposal, its author, its sources, the discussion and the decision (M3).
  • US-9 See disagreement: when a claim is contested, see the alternatives and their evidence; compare views (M3).
  • US-10 Fork a view: create an alternative view of a page or a set of pages, develop it, and propose its changes back (M3).
  • US-11 Govern: read the wiki’s policy; propose a change to it; see who may do what and why (M4).
  • US-12 Moderate: hide harmful content with a reason, visibly; appeal a decision (M4).
  • US-13 Leave or arrive: export the whole wiki as a bundle or as a prikk archive; import a wiki from MediaWiki, BookStack or another inklkunn (export M1; import M5).
  • US-14 Integrate: read and write through an API with scoped tokens; follow changes by feed (M5).
  • US-15 Embed: a planeter user reaches a project’s wiki already signed in, with the same vocabulary and the same trust labels (the module).

4. Content model (CM-…)

  • CM-1 — One wiki is one prikk repository whose worktree is a Portable Wiki Bundle (DR-5; wiki-commons chapter 10): wiki-bundle.yaml as the manifest, pages/ with one Markdown file per page and directories as hierarchy, attachments/ with sidecar metadata, and reserved directories for the knowledge and governance objects of CM-7. The repository is readable by any prikk at or above the floor and by any bundle importer, with no inklkunn running.
  • CM-2 — A page is a Markdown file in the Portable Wiki Markdown profile, Layer 2 (MKUP-1 … MKUP-16), with YAML frontmatter (META-1): title required; id a UUID (version 7) assigned at creation and stable under rename (NAV-9, META-2); aliases; tags; kind ∈ {page, category, template, help, system, redirect, discussion} (META-7); status ∈ {draft, wip, stable, deprecated, archived} (META-6); lang (BCP 47, META-10); license (SPDX, overriding the wiki default, META-9); maintainers (stewards, COLL-11); description; visibility as an advisory signal (META-13). Unknown keys are preserved (META-11). Frontmatter is content: versioned, diffed and attributed like the body (META-14).
  • CM-3 — Names and links. A page is addressable by title and by id. Free links take the profile’s forms, [[Title]], [[Title|label]], [[Title#Heading]], [[Title#^block]], [[ns/Title]], [[prefix:Title]] (MKUP-4). Names are flat with optional / hierarchy (NAV-6, MKUP-7). Resolution follows a documented, tolerant order: exact title, alias, case-insensitive, normalized, hierarchy fallback (MKUP-5). Titles are Unicode, NFC-normalized, and readable in every script in URLs (I18N-1, I18N-2).
  • CM-4 — Dangling links are saved, rendered distinctly, and lead to creation (NAV-3), never by color alone. Backlinks are computed, never maintained by hand (NAV-4). Redirects and aliases keep old titles working across renames (NAV-8, HIST-6).
  • CM-5 — Block identifiers. A paragraph, list item, quotation, table or code block may carry a trailing ^id (MKUP-9); ids are unique within a page and stable over time; claims, inline comments and provenance anchor to [[Page#^id]] (NAV-10). The service assigns an id to a block that a claim or comment attaches to, as part of the accepted change, and never silently changes an existing id.
  • CM-6 — Attachments live under attachments/ with sidecar metadata (filename, media type, SHA-256, size, alt text, license, attribution, uploaded by and when; XFER-4), are referenced relatively, deduplicated by hash, bounded in size (PERF-4), and never hotlinked from remote hosts by default (AUTH-7, PRIV-4).
  • CM-7 — State classes (register item 4). VCS-authoritative (in the repository, signed, sealed, exported): pages, attachments, the manifest, knowledge objects (claims, evidence, decisions, under knowledge/) and governance objects (policies, roles, under governance/). Service-authoritative, append-only (in the service’s store, exported as the bundle’s discussions and as records): proposals’ drafts and review state, comments and decisions on proposals, moderation actions, the audit log, the inclusiveness metrics. Derived or ephemeral (never authoritative): rendered HTML, backlink and search indexes, sessions, notification queues. Every derived view is reconstructible from the two authoritative classes (C-11), and a test proves it by rebuilding with the derived store cleared.
  • CM-8 — Templates, starters and help are pages (kind: template | help | system), editable and versioned like any other (AUTH-6, COLL-12). A template is optional starter content, never a required form.
  • CM-9 — Unfinished is a valid state. status: draft (visible to its author) and wip or a stub (visible to all, marked as unfinished) are respectable; readers can find pages that want help (AUTH-4).
  • CM-10 — Shared artifact, not possession. No page is locked to its creator; maintainers names stewards who are notified and asked to review, never owners who control (COLL-11).
  • CM-11 — Views are branches. A view is a named branch of the wiki repository. Every wiki has a default view (its main branch), which readers see unless they choose another; an alternative view records where it came from (forked_from: view, page, revision; COLL-13). The word canonical is not used anywhere a reader can see it (register item 10).

5. Reading (RD-…)

  • RD-1 — Rendering. The profile renders to semantic HTML (MKUP-12): landmarks, one h1, heading ids, the wikilink and wikilink-missing classes with data-wiki-target, lang attributes, <time> for dates, rel="nofollow ugc" on external links; readable without scripts (WEB-1); sanitized (SEC-2). Callouts, footnotes, tables, task lists, math and diagram code blocks degrade per the profile’s ladder; an unknown directive renders its fallback (EXT-3); transclusion ![[Page]] is depth-limited, cycle-safe and shows its provenance (NAV-16).
  • RD-2 — Every page shows its title and place (NAV-11); the view it belongs to when not the default; created and last changed and by whom (HIST-11); its license (LIC-1); its status when not stable; the repository’s verification state (RD-4); one-step affordances to history, discussion, “propose a change” and the raw source; link relations in <head> (alternate text/markdown, canonical, bookmark, edit, version-history, license, replies, describedby) and schema.org JSON-LD (META-12; wiki-commons chapter 11 §3).
  • RD-3 — History. Per page, the list of changes from prikk with time, the human author (ID-4), the acceptor, the summary, and the minor and automated flags; a diff between any two revisions with word-level highlighting, accessible without color (ins/del, a text summary, keyboard navigation; HIST-2, A11Y-5); permalinks to a revision and to a diff (HIST-5); rename and metadata events shown as events (HIST-6).
  • RD-4 — Verification honesty. Pages carry the repository’s verification state in planeter’s words: Verified (prikk ran its checks just now and found no problems), Verification failed, Could not be checked now. The state is re-derived for display and never served stale as a security display. Content held for review (a proposal) is never shown as part of the record (planeter RFC 003 D-5, RFC 005 D-10).
  • RD-5 — Backlinks with their linking context on every page; unlinked mentions are optional (NAV-4).
  • RD-6 — Health views: wanted pages, orphans, dead ends, broken redirects, pages wanting help, stale pages — framed as opportunities, each with the action that resolves it (NAV-15).
  • RD-7 — Recent changes for the wiki, filterable by namespace, view, minor, automated and kind, with Atom feeds for the wiki, a namespace and a page (COLL-1, API-6); respects the viewer’s access and says when results are filtered.
  • RD-8 — Watch a page or a namespace into a personal watchlist and optional notifications (COLL-2; PR-11). From M2.
  • RD-9 — Search: titles and aliases from M1, full text from M2, with tokenization that handles languages without word delimiters and folds diacritics and width variants (I18N-4); “search or create” with similar-title suggestions before creating (NAV-5); an OpenSearch description (API-7).
  • RD-10 — Raw source URL per page (API-2): the stored file byte for byte, typed text/markdown; charset=UTF-8 with the profile named, with ETag, Last-Modified and Link relations.
  • RD-11 — Freshness. Created, updated and optional verified-on markers; staleness signals and update requests in the health views (HIST-11).
  • RD-12 — Alternative views. When a page differs across views, the page says so and offers a comparison (M3; KN-5).
  • RD-13 — “Why is this here?” From any block, the trace proposal → author → sources → discussion → decision (M3; KN-6).
  • RD-14 — Beginner mode is the default. The default page shows little; history, provenance, verification detail and governance are one step away (PU-6; the main transcript’s “beginner mode”).

6. Proposing, review and acceptance (PR-…)

  • PR-1 — Every change to VCS-authoritative content is a proposal (PU-1). There is no direct-edit path for anyone. A wiki’s policy may let a role accept its own proposals (GV-1), which still leaves a proposal record.
  • PR-2 — A proposal is a first-class object with a URL and a state ∈ {open, accepted, declined, withdrawn, superseded}. It carries the target view; one or more target pages, or a new page; the proposed content; a summary of what and why (AUTH-10); optional sources; the base revision it was made against; its author; and its own revisions, since a proposer may revise an open proposal. Approvals are bound to the proposal revision that was reviewed and never carry over silently (planeter RFC 005 D-5).
  • PR-3 — Proposing needs no markup knowledge and no script. From a page or a section a reader proposes through a plain-text form with a server-rendered preview and a “show changes” diff before submitting (AUTH-1, AUTH-3, AUTH-5, WEB-1); input is accepted tolerantly (AUTH-13). Section- and block-scoped proposals merge independently when they do not overlap (HIST-9). A richer editor is a later progressive enhancement with its own accessibility and input-method review (roadmap R6; A11Y-2, I18N-7).
  • PR-4 — Proposing never requires a key. The service signs on acceptance (DR-4; ID-3 … ID-5).
  • PR-5 — Review: a discussion thread on the proposal; inline comments anchored to blocks with robust selectors (COLL-5; the W3C Web Annotation selector model); per-reviewer decisions approve or request changes, bound to the proposal revision; required approvals per policy (GV-1).
  • PR-6 — Acceptance is one action by an authorized role. The service re-authors the proposal against the current tip of the target view if the base moved (a content-level three-way merge of each page, INT-7); on overlap it shows both texts and stops, discarding neither (HIST-9), and the proposer or the acceptor resolves by revising; then it commits and seals under the wiki’s keys (INT-4), updates the page, and records the resulting change (block and patch ids) on the proposal. Acceptance is atomic from the person’s view: either the change is in the history and the proposal is accepted, or nothing changed and the reason is named (DUR-2).
  • PR-7 — Decline and withdraw carry a reason, visible on the proposal, worded by a template that assumes good faith and names the next step (COLL-7, HIST-3); the proposer is told (PR-11).
  • PR-8 — Undo is a proposal. A rollback proposal re-applies the inverse at content level and goes through the same loop; history is never rewritten; the result names the change it undoes (HIST-3). prikk’s own rollback vocabulary stays internal.
  • PR-9 — Gentle guidance. Lint findings (a dangling link, missing alt text, a missing source, a skipped heading level) appear in the preview and in health views as suggestions, never as blockers (AUTH-13; A11Y-2 Part B).
  • PR-10 — Never lose a draft. A proposal in progress is saved server-side as a private draft, survives session expiry and re-authentication, and is findable (“you have an unsent proposal”) (AUTH-8, SEC-3).
  • PR-11 — Notifications with restraint. A person is told of events that involve them (their proposal reviewed, accepted or declined; a reply; a mention; a watched page changed); everything else is a feed. Channels and digests are the person’s choice. A notification never carries content the recipient could not read (COLL-9, PRV-5).
  • PR-12 — Attribution and authority are visible. An accepted change shows the proposer as its author and the acceptor as the deciding maintainer, with the role and policy version that authorized the acceptance (HIST-4; main transcript, “make authority visible”); both are in the signed message (ID-4) and in the service’s records.
  • PR-13 — Flags. Minor and automated (bot) proposals are flagged and filterable; machine-assisted content is labelled and attributed to the human who accepted it (HIST-8, AUTH-14).
  • PR-14 — Quotas and rate limits per principal and per wiki (open proposals, accepted bytes, revisions per proposal); a refusal names the limit and the way out (register item 7).
  • PR-15 — A proposal may touch several pages, including a rename together with edits, and is accepted as one change (INT-4).
  • PR-16 — A thanks action on an accepted proposal (COLL-7). Optional; from M2.
  • PR-17 — Per-page discussion (“talk”) is separate from proposal review, durable, attributable, resolvable and exportable (COLL-3, COLL-4, XFER-10); discussion kinds are distinguished (KN-7).

7. Knowledge layer (KN-…) — M3; RFC 005

  • KN-1 — A claim’s identity is distinct from its expression. A claim has one or more expressions (wordings) anchored to page blocks across views, and relations to other claims: refines, contradicts, supersedes. An edit to wording does not create a new claim unless the meaning changes. The rule that decides when identity changes is RFC 005 part 1’s, validated by prototype before part 2 is designed (register item 1; C-5).
  • KN-2 — Epistemic status has several dimensions and never one score (register item 2; NG-3): lifecycle (proposed, adopted, retired), community status (accepted, contested, unresolved), evidence state (supported, mixed, challenged), scope (the default view, a named view). Unresolved and unknown are legitimate states, not errors.
  • KN-3 — The kind of a statement is recorded (register item 20): observation, interpretation, hypothesis, opinion, decision, policy, question — enough to present and govern each appropriately, not a universal ontology.
  • KN-4 — Evidence carries a source identity, a reference and where possible an archived snapshot, an interpretation or context, its relation to the claim (supports or challenges, with a stated strength), and provenance. Evidence can be challenged, shared across claims and superseded (register item 3).
  • KN-5 — Disagreement coexists (principle 3). A contested claim shows its alternatives and their evidence; the default view is a community decision with a visible history, never a truth mark; evidence strength is shown and equal weighting is not implied (main transcript, message 4 §6).
  • KN-6 — Provenance. For any block, the chain proposal → author → sources → discussion → decision → change is derivable from prikk history and the service’s records (RD-13).
  • KN-7 — Discussion kinds (register item 5): epistemic (about a claim), proposal review, governance, moderation, social — each with its own visibility, retention and export rule.
  • KN-8 — Freshness. When evidence was last reviewed is recorded, and stale evidence is surfaced (HIST-11; the main transcript’s “knowledge freshness”).
  • KN-9 — Fork kinds are named (register item 6): a technical fork (an experimental view), an interpretive fork (a competing understanding) and a governance fork (different rules) are presented differently. Cross-wiki forks are out of v1 (NG-5; wiki-commons FED-3).

8. Governance and moderation (GV-…) — M4; RFC 006

  • GV-1 — Policy is data. Each wiki has a policy, versioned under governance/, stating who may read, comment, propose, review, accept, create views, moderate and administer; how many approvals an acceptance needs; whether anonymous proposing is allowed; how disputes are handled. A policy change is a proposal under a constitutional layer (register item 13): the operator’s platform constitution (set by configuration) above the wiki’s constitution (changeable only by its admin role) above the wiki’s policy (changeable by the policy’s own rule) above object-level settings. The history explains why the rules are what they are.
  • GV-2 — The participation ladder is roles: visitor, observer, questioner (comment), contributor (propose), reviewer, maintainer (accept, moderate), admin. Promotion criteria are explicit policy data (time, accepted proposals, a maintainer’s decision). No opaque aggregate reputation value is ever a prerequisite (register item 9; C-12).
  • GV-3 — Authority is visible (PR-12): every decision names the role and the policy version that authorized it.
  • GV-4 — Soft security first (COLL-6). Revert, visibility and discussion before locks. Protection (review required, acceptance restricted) is per namespace or page, progressive, time-limited by default, and shown on the page with its reason (COLL-10).
  • GV-5 — Moderation hides, it does not erase. A proposal’s, comment’s or revision’s content, summary or author can be hidden behind a tombstone that keeps the item’s existence and position and states the reason category and the acting role; the action is logged, reversible and appealable (HIST-12, TRUST-3).
  • GV-6 — Deletion. Pages are soft-deleted and recoverable (HIST-7); links to them become dangling links, never dead ends. Permanent removal for legal or privacy reasons is a documented operator procedure that states its costs (prikk cannot remove an object: the repository is re-created without the content, and the ids and permalinks of the affected history change) and it exists before any public deployment (register item 14).
  • GV-7 — Adversarial resistance (register item 7): rate limits and quotas (PR-14); progressive friction for new accounts set by policy; proposal-spam and sock-puppet signals surfaced to maintainers from the audit log, never automatic bans. The wiki must remain usable and governable under adversarial participation without making legitimate low-friction contribution impossible.
  • GV-8 — Appeals. A findable path exists to contest a decline, a moderation action or a role decision (TRUST-3).
  • GV-9 — Inclusiveness is measured (register item 18), from the service’s records, for maintainers: time to first proposal, proposal abandonment rate, the share of proposals that received substantive feedback, first-proposal acceptance rate, review turnaround, contributor return rate, and the concentration of accepted changes among the most active contributors. A product-health view, never a per-person score shown publicly unless the wiki’s policy says so.
  • GV-10 — Licensing. A default content license per wiki (DR-8: CC BY-SA 4.0 for public wikis) is declared on every page, in the HTML head, the site description and the bundle manifest (LIC-1); shown at the moment of proposing (LIC-2); overridable per page and per attachment with SPDX identifiers (LIC-3); attribution is satisfied by the history and the contributors view (LIC-4); a relicensing is an event in history (LIC-6).

9. Identity, keys and signing (ID-…)

  • ID-1 — Accounts. Local passwords (Argon2id) and OpenID Connect sign-in; sessions with CSRF protection; scoped, expiring, revocable tokens for the API; a display name is one free-text field in any script, never split or truncated (planeter RFC 012 D-6); email is private.
  • ID-2 — Pseudonymous participation is possible. Reading is anonymous. Anonymous proposing and commenting are wiki policy options, off by default (OQ-1), realized with temporary pseudonyms and never with published addresses (PRIV-3).
  • ID-3 — Signing (DR-4). Each wiki has its own author key and maintainer key, generated with prikk’s key tooling, held by the service encrypted at rest under an operator-provided secret, never shared across wikis. The maintainer key is adopted in the repository’s trust store; the service is the repository’s sole writer (INT-2). Key rotation (a new key id adopted, the old one removed from trust) and compromise handling are documented procedures (SEC-4). Fact: prikk has no author-key revocation, so an author key rotates by a new key id (UD-5).
  • ID-4 — Attribution in the record. Every patch message carries, in a stable machine-readable form, the proposal id, the proposer’s account id and display name at the time, and the acceptor’s account id. Fact: prikk stores the commit message as a signed, identity-bearing field (prikk RFC 123). The service’s records hold the same, so attribution can be cross-checked and survives either store.
  • ID-5 — Honesty labels. Content signed by the service is labelled as such (“signed by the wiki service on behalf of …”); no label implies that a person signed cryptographically.
  • ID-6 — Later opt-ins, reserved and not v1: per-account author keys held by the service; bring-your-own key with client-side signing for maintainers (DR-4 options b and c).
  • ID-7 — Authorization. One pure, default-deny authorize(principal, action, resource) is consulted on every path: web, API, feeds, search, export. Actions: read, comment, propose, review, accept, create-view, moderate, admin, export, import. Resources: wiki, namespace, page, view, proposal, discussion. A private resource denies identically whether or not it exists (planeter RFC 002).
  • ID-8 — Audit log. Security- and governance-relevant events (sign-in, role changes, acceptances, moderation, key operations, exports and imports) are recorded append-only, exportable off-box, as events and never as content (COLL-8; wiki-commons SEC-5).
  • ID-9 — Trust vocabulary. The wiki reuses planeter’s words where the concept is the same (Verified, Verification failed, Could not be checked now, Signed into the history) and adds its own for the proposal loop (held for review, accepted, declined); the glossary fixes them (INC-3).

10. Interchange and API (IX-…)

  • IX-1 — Export a wiki as a Portable Wiki Bundle (XFER-1 … XFER-15): pages and attachments as stored; history as JSON Lines derived from prikk (XFER-7) with revisions, authors, summaries, renames and tombstones; discussions from the service’s records (XFER-10); a contributor directory with a pseudonymization option (XFER-8); a manifest declaring fidelity, the interwiki map and checksums (XFER-1, XFER-2); a dry run; incremental scope, a page or a namespace (XFER-14).
  • IX-2 — Export the repository itself as a prikk archive and as a bundle (prikk archive export, prikk bundle export) for an admin (NG-7); anyone holding the repository can prikk verify it (PU-3).
  • IX-3 — Import a Portable Wiki Bundle (fidelity levels 0 to 3, discussions at level 4 when present) as an admin action that becomes commits in the wiki’s repository, with attribution carried as history records allow (LIC-4), an import report (XFER-13), a license compatibility check (LIC-5) and untrusted-input handling (SEC-5). MediaWiki and BookStack arrive through wiki-commons’ tooling (M5).
  • IX-4 — API. REST over HTTPS, described in OpenAPI (API-1). Reads: pages (enumerate, get, raw source, HTML fragment), history, revisions, diffs, backlinks, health views, search, recent changes, proposals, discussions. Writes, per authorization: propose, revise, comment, review, accept, with optimistic concurrency by ETag or base revision (API-11). Errors as problem details (RFC 9457) with stable codes; Link pagination; rate-limit headers; scopes enforced per endpoint (API-13, API-14); planeter’s API conventions where the two overlap.
  • IX-5 — Feeds. Atom for the recent changes of the wiki, a namespace and a page, and for proposals (API-6).
  • IX-6 — Discovery. A site description document (API-1); link relations in every page head (chapter 11 §3); an OpenSearch description (API-7); a sitemap and robots.txt for public wikis; the interwiki map published (API-9).
  • IX-7 — Webhooks (later): HMAC-signed, delivered through the egress guard, SSRF-safe (API-15).
  • IX-8 — Conformance. A wiki-commons.yaml self-assessment is published with each release, with versioned claims (@0.4): core-reading and portable-content from M1; living-history, open-collaboration, accessible-authoring and many-languages as M1 and M2 deliver them; trustworthy-operation before 1.0 (OQ-4 for the final set).
  • IX-9 — Interwiki links [[prefix:Title]] resolve through a per-wiki map; links between wikis of one inklkunn resolve natively (NAV-13).

11. The planeter module (MD-…) — joint RFC 008; theme T8

  • MD-1 — Process boundary. inklkunn runs as its own service with its own repositories, keys and threat model. planeter never holds inklkunn’s keys and never writes to a wiki repository; the default planeter build stays keyless (planeter INV-2).
  • MD-2 — Shared identity. A person signed in to planeter is recognized by inklkunn without a second sign-in. The mechanism (a common OpenID Connect provider, planeter-issued tokens, or a trusted-proxy contract) is RFC 008’s to decide (OQ-2).
  • MD-3 — Authorization alignment. A wiki attached to a planeter repository or organization inherits its visibility and maps planeter’s roles onto wiki roles by an explicit, documented table; a standalone wiki uses its own policy. authorize() stays single and default-deny on both sides.
  • MD-4 — One product to the person. planeter’s navigation gains the wiki; the wiki keeps planeter’s conventions (language choice carried over, the glossary’s words, the same trust labels, the same accessibility baseline); a person never meets two vocabularies for one concept (MD-7).
  • MD-5 — Independent verification. The wiki’s repository can be registered in planeter as a read-only hosted repository, so Verified can be checked by a path the wiki does not control.
  • MD-6 — Cross-references (the main transcript’s phase 2, later): issues, changes and wiki pages link each other by URL first and by id later; code-to-knowledge provenance (phase 3) is out of v1.
  • MD-7 — Vocabulary alignment. Proposal (a change under review) and change (a sealed block) mean the same in both products; inklkunn’s glossary extends planeter’s with page, view, claim, evidence, decision and policy.

12. Non-functional requirements

12.1 Security (SEC-…)

  • SEC-1 — A threat model is a first-class deliverable: v0.1 with the design set; updated by any release touching identity, signing, the prikk boundary, rendering or inbound content; re-verified by the others (project rules).
  • SEC-2 — Rendering untrusted content. An allowlist sanitizer on everything rendered; a strict Content Security Policy with no inline script; nosniff, frame protections and a Referrer-Policy; raw source, attachments and any user file served from an isolated origin (wiki-commons SEC-1, SEC-2; planeter STD-6).
  • SEC-3 — State changes need intent. CSRF protection on every cookie-authenticated write; re-authentication for sensitive actions; a session expiry never discards a draft (wiki-commons SEC-3).
  • SEC-4 — Keys. Generated by prikk’s tooling; stored encrypted at rest under an operator secret; never in content, frontmatter, bundles, logs or error texts (wiki-commons SEC-8); rotation and compromise procedures documented; the signing component isolated from the web tier by a process or module boundary the design enforces.
  • SEC-5 — Untrusted input. Imported bundles, pasted content, uploaded attachments and API bodies are untrusted: path traversal, archive bombs, oversize and type mismatch are refused by name (wiki-commons SEC-7); prikk runs sandboxed (INT-1); no content-provided code executes (NG-8).
  • SEC-6 — One egress guard for every outbound fetch (OpenID Connect discovery, interwiki checks, link previews, webhooks): no loopback, private or link-local target unless allow-listed (planeter C-8).
  • SEC-7 — Bounded operations. Every prikk call runs under a time and memory budget (the planeter RFC 011 pattern); page, proposal and attachment sizes are bounded (PERF-4); refusals are honest (too large, busy), never silence or an out-of-memory kill of the server.
  • SEC-8 — Supply chain. Pinned, locked, audited dependencies; cargo deny and cargo audit at every project event; forbid(unsafe_code) in every crate; a license allow-list; every new dependency measured and reviewed before adoption (planeter’s dependency policy, adopted).
  • SEC-9 — Secrets committed into pages are carried faithfully by prikk and cannot be un-leaked; the risk is stated to operators; detection is optional, later (planeter T-14).
  • SEC-10 — A security policy and advisories (SECURITY.md, security.txt; wiki-commons SEC-10).

12.2 Privacy (PRV-…)

  • PRV-1 No third-party trackers, fonts or CDNs; assets self-hosted; what is logged and for how long is stated (PRIV-1, PRIV-2).
  • PRV-2 Contributor identity: pseudonyms allowed; addresses never published; emails private and never exported; exports pseudonymizable with the manifest saying so (PRIV-3, XFER-8).
  • PRV-3 A person can export their own profile and contributions; account deletion replaces the name with a stable pseudonym and keeps history, as documented (PRIV-5).
  • PRV-4 Private wikis: search, feeds, backlinks, sitemaps and link previews respect visibility; pages carry noindex; errors are existence-neutral (PRIV-7).
  • PRV-5 Notifications do not leak content (PRIV-6).
  • PRV-6 Nothing is fetched on a reader’s behalf without consent: no remote image hotlinking by default; embeds are click-to-load (PRIV-4).

12.3 Inclusion: accessibility, language, words (INC-…)

  • INC-1 — WCAG 2.2 level AA for reading, proposing, reviewing and administering; ATAG 2.0 Parts A and B for authoring; structural tests that fail the build: one h1, landmarks, a skip link, labels, alt text, lang and dir, contrast in both color schemes, visible focus, 24 px targets, reflow at 320 px, reduced motion, no information by color alone, accessible diffs; an accessibility statement per release naming what was and was not checked by people (planeter RFC 012 D-1, D-2, D-5; A11Y-1 … A11Y-11).
  • INC-2 — Language. A message catalog with stable keys, whole sentences, named placeholders and plural rules; English and Japanese (DR-7); negotiation by Accept-Language with a switcher that needs no script and keeps its choice in a cookie; <html lang> and dir; logical CSS properties from the start; per-page lang and per-fragment marking; Japanese ships only after a fluent reviewer’s pass (RFC 012 D-3; I18N-3, I18N-5).
  • INC-3 — Plain words. A glossary fixes every user-facing term, reusing planeter’s where the concepts overlap. The VCS vocabulary (commit, seal, rebase, patch, block, ref) never appears in user-facing text except inside the explanations a reader opens on demand. Every error and empty state names a next step; no gendered words; calm tone; inclusive technical vocabulary (RFC 012 D-4, D-6; main transcript §8).
  • INC-4 — No script required to read, propose, review or administer; enhancements are progressive and obey the input-method rule (I18N-7).
  • INC-5 — Performance as inclusion. Small pages, one stylesheet, no web fonts, no third-party requests (WEB-4).
  • INC-6 — A newcomer path. A sandbox page or wiki (AUTH-9); help and conventions as pages linked from the proposal form (COLL-12); a welcome on a first proposal and respectful templates for declines (COLL-7); the ladder and its criteria visible (GV-2).
  • INC-7 — Unicode everywhere. Titles, tags, link targets and names in any script; NFC normalization; locale-aware sorting; explicit time zones (I18N-1, I18N-4, I18N-9).
  • INC-8 — Print and text-only readers work; light and dark schemes with sufficient contrast (WEB-2).

12.4 Performance and scale (PERF-…) — provisional targets, to be calibrated by measurement in M1 and M2

  • PERF-1 — Reads do not re-run prikk per request. A derived cache keyed by prikk’s content-addressed ids, invalidated when a view’s tip moves, never authoritative and never used for a security display (CM-7, RD-4). Provisional target: a cached page view under 100 ms of server time at the 95th percentile; a cold page under 1 s on a wiki of 10,000 pages.
  • PERF-2 — Acceptance end to end (merge, commit, seal, cache update) under 5 s at the 95th percentile for a typical page on a wiki with 10,000 changes. Proposals are serialized per wiki (INT-2) and the queue is visible: busy with a wait estimate rather than silence.
  • PERF-3 — Scale targets for 1.0: 10,000 pages and 100,000 changes per wiki; 100 concurrent readers per node; tens of wikis per instance; measured on a reference corpus kept in the repository (prikk’s RFC 139 corpus is the precedent).
  • PERF-4 — Bounds. Page source 1 MiB, attachment 25 MiB and proposal 2 MiB by default, configurable by the operator within prikk’s object bound; every prikk call under a memory budget with a per-call ceiling (SEC-7).

12.5 Durability and recovery (DUR-…)

  • DUR-1 — Authoritative state is one set: the wiki repositories, the service store and the key store. It is backed up as one coherent, time-aligned, encrypted set with a rehearsed restore; prikk verify runs after every restore (wiki-commons SEC-9).
  • DUR-2 — An interrupted acceptance leaves no half-state. An intent record is written before the write; recovery runs after a crash; the wiki refuses writes and still serves reads until recovered; every step is recorded (the planeter RFC 004 recovery pattern, adapted).
  • DUR-3 — prikk format. The serving binary stays at or above the format its repositories carry; inklkunn never upgrades a repository’s format without an intended operator act; re-baseline at each prikk release (UD-1).
  • DUR-4 — Export is part of disaster recovery. The bundle export and the prikk archive are tested restores, not only features.

12.6 Operations (OPS-…)

  • OPS-1 — One server binary and a container image; configuration by documented environment variables that --help lists; SQLite by default behind store traits with a PostgreSQL path; Linux (the sandbox, OQ-3); prerequisites named: prikk at the floor, bubblewrap, prlimit, and curl where the planeter pattern for confined outbound HTTPS is reused.
  • OPS-2 — Behind a TLS-terminating reverse proxy with declared trusted proxies; a non-loopback bind is refused without them (planeter TB-8).
  • OPS-3 — Observability. Structured logs that carry no content; a health endpoint; counters for admissions, refusals, acceptances and queue depth; metrics export later.
  • OPS-4 — Releases. Signed bare X.Y.Z tags, attested artifacts, a CHANGELOG with “Upgrading” and “Output changes” sections, crates published as an install path; the architect proposes a cut, the owner authorizes (ROADMAP §5).
  • OPS-5 — Documentation. A concise README in the project rules’ structure; docs/src as an mdBook organized for new users, intermediate users (API, functional specification) and maintainers (the design set); the wiki documents itself where it can, its help pages being a wiki (COLL-12).
  • OPS-6 — The operator can see which prikk version runs, which format each repository carries, and each wiki’s verification state.

13. prikk integration (INT-…) and boundaries (BN-…)

  • INT-1 — The prikk CLI is driven as a sandboxed subprocess with --format json; no prikk crate is linked (DR-3; prikk RFC 145). The driver sits behind a storage trait so that another backend, or a future prikk library if prikk ever rules one stable (RFC 170, not assumed), replaces it without reworking callers. The prikk version is pinned with a floor and checked at start; an unknown schema_version is a refusal, never a guess.
  • INT-2 — One prikk repository per wiki; inklkunn is its sole writer under the wiki’s own author and maintainer keys. Writes are serialized per wiki by a lease above prikk’s fail-fast locks; a lock conflict or a stale lock is surfaced to the operator and never cleared automatically (prikk’s own rule).
  • INT-3 — Reads are re-derived from prikk (log, show, tree, cat, diff, extract, branch, tag, verify) and cached by content-addressed id; prikk is the source of truth for history and verification.
  • INT-4 — The write path of an acceptance: bring the wiki’s worktree to the target view’s tip (branch switch when the view differs); apply the merged change to the files; declare renames with prikk mv; prikk commit -m with the ID-4 message under the author key; prikk seal --allow-no-audit under the maintainer key; confirm publication; update the cache. Each accepted proposal is traceable to exactly one patch, or to a declared set, and to the block that sealed it.
  • INT-5 — Operation mapping. A new page is a created file; an edit is a text edit whose span prikk authors; a rename is a declared move; a removal is a deleted node; an attachment is a created file or a binary replacement; symbolic links never exist (prikk refuses them).
  • INT-6 — Verification. prikk verify runs after every seal and on a schedule; a wiki whose last verification failed refuses acceptances and says why; results are shown per RD-4.
  • INT-7 — Content-level merge is inklkunn’s. A proposal whose base moved is re-authored by a three-way merge of each page’s text against the current tip; overlapping changes are presented and never auto-resolved, consistent with prikk’s own refusal; the proposal’s base and the merge result are recorded (roadmap R2).
  • INT-8 — Views are branches. A view is created with branch create heads/<view> --from <ref>; its changes are proposals accepted on that branch; bringing a view’s changes to the default view is a prikk merge when the two are proven confluent and a content-level proposal when they are not. RFC 005 fixes the rule.
  • INT-9 — Gaps are named, not faked. What prikk does not expose (blame or annotate, a patch’s size) is shown as pending a prikk increment and asked by letter (UD-10).
  • INT-10 — The repository stays an ordinary prikk repository. Nothing inklkunn-specific lives inside .prikk/; everything inklkunn needs is in the worktree (the bundle) or in its own store.

Boundaries:

  • BN-1 — inklkunn owns pages and the wiki semantics, proposals and review, the knowledge and governance layers, identity above prikk, the web and the API, and the honest mapping of its decisions onto prikk’s signatures.
  • BN-2 — prikk owns the repository: history, signatures, verification, patch algebra and artifact formats. inklkunn drives these; it does not redefine them (NG-2).
  • BN-3 — planeter owns the forge: software repositories, forge identity, and the read-only hosting of a wiki’s repository when it is registered there (MD-5).
  • BN-4 — wiki-commons owns the vocabulary and the interchange conventions. inklkunn adopts them and reports what it learns back (an engine profile, corpus cases) instead of diverging silently.
  • BN-5 — inklkunn never pushes weight into prikk or planeter. A capability that cannot be built without changing either is refused or deferred, and the reason is recorded.

14. Architectural constraints (C-…) — binding unless revised by an approved decision

Carried verbatim in substance from the requirements analysis (the Role & System Frame, §4):

  1. C-1 The VCS is the substrate, not the user interface or the social model; ordinary users never need to understand commits, branches, merges or other VCS mechanics.
  2. C-2 Knowledge is modeled as revisable claims; claims, evidence, proposals, discussions, decisions, policies, provenance and views remain explicit domain concepts.
  3. C-3 Proposals and patches are distinct: a proposal is a human and social operation; a VCS patch is the durable state transition that implements an adopted change.
  4. C-4 Rendered pages and other views are projections, not the authoritative knowledge state.
  5. C-5 Claim identity is stable and independent of page location or presentation.
  6. C-6 Disagreement is representable without premature destructive resolution.
  7. C-7 Governance and consequential authority are explicit, inspectable, and versionable where appropriate.
  8. C-8 Authorization is enforced below the UI layer.
  9. C-9 Provenance and attribution are first-class integrity requirements.
  10. C-10 The core remains domain-neutral and does not make wiki pages or hierarchical documents its fundamental storage abstraction. Reading under DR-1: pages are the stored artifact of the first application, held in the bundle layout; the domain model names claims, evidence, views and decisions as objects of their own, so a later application is a new projection, not a rewrite.
  11. C-11 Derived indexes, caches and projections are reconstructible from authoritative state.
  12. C-12 The architecture does not depend on a universal numeric truth or reputation score.
  13. C-13 AI may assist knowledge formation but never silently becomes an authority over truth, governance or durable knowledge state.
  14. C-14 Privacy, moderation, deletion, legal constraints and historical integrity are potentially conflicting requirements; immutable history is not treated as absolute.
  15. C-15 Inclusiveness means low barriers to legitimate participation while retaining effective safeguards against abuse and authority capture.
  16. C-16 Implementation technology and deployment decomposition are not frozen prematurely where architectural evidence is still required.

2. Surfaces

2.1 Web surface (WEB-…)

All pages are server-rendered, work without scripts (INC-4), carry the catalog’s words in the reader’s language (INC-2), pass the structural accessibility checks (INC-1), and consult authorize() (ID-7).

  • WEB-01 — Wiki home and page view (RD-1, RD-2, RD-14). A page shows its title and place, the view when not the default, the body rendered from the profile, created and changed and by whom, its license, the verification badge, and one-step links: history, discussion, Propose a change, raw source, backlinks. Dangling links are marked and lead to Propose a new page. Depth (provenance, verification detail, governance) is behind Details.
  • WEB-02 — History, diff and permalinks (RD-3). The change list for a page; a diff between any two revisions with word-level marks and a text summary; a permalink to a revision renders the page at that point and says so, linking to the current one.
  • WEB-03 — Propose (PR-3). From a page or a section: a form with the current text, a summary field (“what and why”), optional sources, Preview and Show changes (server round trips), Save as draft and Submit. Lint findings appear as suggestions (PR-9). Submission yields the proposal page. A signed-out reader sees the form’s existence and is asked to sign in (or, when the wiki’s policy allows anonymous proposing, to continue under a temporary pseudonym; OQ-1 default off).
  • WEB-04 — Proposal page and review (PR-2, PR-5, PR-6, PR-7). The proposal’s state, author, target, summary, what it changes (page by page, block by block), the discussion thread, inline comments anchored to blocks, decisions per reviewer bound to the revision, and the actions the viewer’s role allows: comment, approve, request changes, accept, decline, withdraw, revise. A stale base shows re-authored against the current page; an overlap shows both texts and asks for a revision. An accepted proposal links to its change in the history.
  • WEB-05 — Discussion (PR-17). A page’s talk, threaded, resolvable, attributable; kinds labelled (KN-7).
  • WEB-06 — Recent changes, search and health (RD-6, RD-7, RD-9). Filterable recent changes; search with create “…” when nothing matches; wanted, orphan, dead-end, broken-redirect and wants-help lists, each with its resolving action.
  • WEB-07 — Sign-in (ID-1): local password or single sign-on; accessible authentication (no cognitive test, paste allowed).
  • WEB-08 — Administration (US-A6): create a wiki (name, default view, license, language, policy bootstrap); roles; key status (which key ids, when rotated; never a secret); export (bundle, archive); import with a dry run and a report; the recovery door (DUR-2).
  • WEB-09 — Honesty labels (ID-5, ID-9): Verified, Verification failed, Could not be checked now for the repository; held for review, accepted, declined for proposals; signed by the wiki service on behalf of … on every change. No page says more than is known.
  • WEB-10 — Safe rendering (SEC-2): sanitizer, strict CSP, raw source and attachments on the content origin only.
  • WEB-11 — Knowledge surfaces (M3; GATED-1): claims and evidence on a block, Why is this here?, Show disagreement, view comparison and creation.
  • WEB-12 — Governance surfaces (M4; GATED-2): the policy page, roles and the ladder, protections, moderation with tombstones, appeals, the inclusiveness dashboard for maintainers (GV-9).

2.2 REST API (API-…)

  • API-01 — Described in OpenAPI (IX-4), served at a documented path and advertised from every page by rel="service-desc" (IX-6). Versioned in the path; stable error codes.
  • API-02 — Reads: list pages (cursor pagination, filters: namespace, tag, kind, changed since); a page as JSON (metadata + rendered fragment) and as raw source (RD-10; content negotiation text/markdown); history, a revision, a diff; backlinks and link health; search; recent changes; proposals and their revisions; discussions. Every response carries an ETag; conditional requests are honoured.
  • API-03 — Writes (authorized, scoped): create a proposal, revise it, comment, review (approve / request changes), accept, decline, withdraw; each write names the base revision or If-Match and gets a conflict response when stale (API-11 of wiki-commons).
  • API-04 — Errors are problem details (RFC 9457) with a stable type, a message and a hint in the caller’s language; existence-neutral for private resources.
  • API-05 — Rate limits and scopes: RateLimit and Retry-After headers; token scopes read, propose, review, accept, admin, enforced per endpoint, intersected with the account’s roles.
  • API-06 — Feeds: Atom for the wiki, a namespace, a page, and proposals (IX-5).
  • API-07 — Discovery: the site description document (IX-6), OpenSearch, sitemap and robots.txt on public wikis, the interwiki map.
  • API-08 — Not a second source of truth (NG-6): reads re-derive from prikk and the service records.

2.3 Identity and authorization surface (AUTH-…)

  • AUTH-01 — Sign-in: local passwords (Argon2id) and OpenID Connect (code + PKCE); accounts linked to an issuer and subject administratively or at first sign-in per the wiki’s policy; sessions Secure, HttpOnly, SameSite, with CSRF tokens on every cookie-authenticated write.
  • AUTH-02 — Machine credentials: scoped, hashed, expiring, revocable tokens (API-05).
  • AUTH-03 — Authorization: one pure default-deny authorize(principal, action, resource) (ID-7) consulted by web, API, feeds, search and export; roles per wiki from the ladder (GV-2); visibility public / internal / private is a read gate; a denied private resource is indistinguishable from an absent one.
  • AUTH-04 — Attribution: every proposal, comment, decision and acceptance is recorded against the principal; every acceptance is written into the signed patch message (CT-03).
  • AUTH-05 — Audit log (ID-8), append-only, exportable.
  • AUTH-06 — Shared identity with planeter (MD-2; GATED-3): the mechanism is RFC 008’s; until then a common OpenID Connect provider makes one sign-in serve both.

2.4 prikk-integration surface (PK-…)

  • PK-01 — One repository per wiki, laid out as a Portable Wiki Bundle (CM-1), under an inklkunn-managed root keyed by an opaque wiki id (never the wiki’s name on disk, so renames move no bytes).
  • PK-02 — Reads through the storage driver: branch (views and tips), tree and cat at a point, log and show (history and a change’s content), diff between points, extract of a point into a scratch directory, verify. All --format json; an unexpected schema_version is a refusal (INT-1).
  • PK-03 — Writes only through the signer: bring the worktree to the target view (branch switch), write files, mv for renames, commit -m under the wiki’s author key, seal --allow-no-audit under its maintainer key, verify; branch create for a new view (INT-4, INT-8).
  • PK-04 — Sandbox and pin: every invocation confined (a restricted filesystem view: the repository, the scratch directory and, for writes, the decrypted seed files on a private mount), with a wall-time and memory budget (SEC-7); the prikk version checked at start against the floor.
  • PK-05 — Keys: generated by prikk key generate; adopted with trust maintainer add; key ids inklkunn-<wiki-id>-author and -maintainer; rotation adopts a new id and removes the old from trust (ID-3).
  • PK-06 — Gaps shown, not faked (INT-9).

3. Flows (FL-…)

  • FL-01 — Read a page (US-1). Resolve wiki and title (aliases, redirects, normalization; CM-3) → authorize read → the view’s tip (cached) → the page file at that tip → parse, resolve links, render, cache by content id → the page with its badges. A missing title shows This page does not exist yet with Propose it (NAV-3).
  • FL-02 — Propose (US-3). Open the form on a page or section → draft saved on each preview (PR-10) → submit → the proposal is recorded (service store) with its base revision, content and summary → the proposal page; reviewers are notified per policy (PR-11).
  • FL-03 — Review (US-5). Read what changes → comment inline or in the thread → approve or request changes, bound to the proposal revision → the proposer is told.
  • FL-04 — Accept (US-6). An authorized role accepts → the service takes the wiki’s write lease → checks the base against the view’s tip; if moved, three-way merge per page; on overlap, stop and show both texts (the proposal becomes needs a revision) → writes an intent record (DUR-2) → the signer brings the worktree to the view, applies files and renames, commits with the CT-03 message, seals, verifies → the cache for the view is invalidated → the intent is completed and the proposal marked accepted with the block and patch ids → the proposer is told. Any failure before the seal changes nothing; a failure after it is completed by recovery (FL-10).
  • FL-05 — Decline or withdraw (US-4). A reason is required; the message template assumes good faith and names the next step; the proposer is told.
  • FL-06 — Undo (US-7). Propose a rollback on a change opens a proposal whose content is the inverse at content level; it goes through FL-02 … FL-04 and names the change it undoes.
  • FL-07 — Rename a page. A proposal that changes title and the file path; on acceptance a declared move (mv), the old title kept in aliases (NAV-8, HIST-6).
  • FL-08 — Export (US-13). An admin requests a bundle (fidelity 3, discussions when present, pseudonymization optional) or a prikk archive; the bundle is built from the repository and the service records and offered as a download from the content origin.
  • FL-09 — Import (US-13). An admin uploads a bundle → dry run with a report → confirm → the pages become one or more accepted changes under the wiki’s keys with the import’s attribution in the messages → report kept.
  • FL-10 — Recover after a crash. At start and after an unfinished acceptance: for each wiki with an open intent, check prikk’s locks and doctor, complete or abandon per the witnesses, verify, clear the flag; the administration surface shows the plan and the record (DUR-2).
  • FL-11 — Create a wiki (US-A6). Name, default view, license, languages, policy bootstrap → repository initialized, keys generated and adopted, manifest and help pages written as the first accepted change.
  • FL-12 — Reach the wiki from planeter (US-15; GATED-3). Signed in to planeter, a person follows the wiki link; shared identity recognizes them; roles map by the documented table.

4. External data contracts (CT-…)

  • CT-01 — The page file (CM-2): Portable Wiki Markdown Layer 2 with YAML frontmatter; UTF-8, LF, NFC; the path under pages/ derived from the title by the bundle’s file-name rules (XFER-3), with title and id in frontmatter authoritative. Title-to-path mapping is deterministic, documented, and refuses characters that cannot be a safe path component.
  • CT-02 — The repository layout (CM-1, CM-7): wiki-bundle.yaml, pages/, attachments/ with <name>.meta.yaml sidecars, knowledge/ and governance/ (schemas fixed by RFCs 005 and 006). Nothing of inklkunn’s inside .prikk/ (INT-10).
  • CT-03 — The patch message (ID-4): a first line that is the proposal’s summary, then trailer lines in a stable form, for example Proposal: <proposal id>, Proposed-By: <account id> (<display name>), Accepted-By: <account id>, Base: <block id>, Kind: proposal | rollback | import | system; parsed back by inklkunn and readable by anyone with prikk log.
  • CT-04 — Proposal and review records (service store): proposal {id, wiki, view, state, author, summary, sources, created}, revision {proposal, seq, base block, content per page, created}, comment {anchor (page, block id, quote selector), body, author}, decision {revision, reviewer, verdict}, intent {proposal, revision, wiki, state, attempts}, acceptance {proposal, block id, patch ids, acceptor}.
  • CT-05 — The derived cache: keyed by prikk content ids (block id, blob id) and the catalog language; invalidated when a view’s tip moves; never a security display’s source (RD-4).
  • CT-06 — The bundle export (IX-1): the repository’s files as stored, history/<page id>.jsonl from prikk’s history with the CT-03 attribution, discussions/ from the service records, users.yaml, manifest with fidelity and checksums.
  • CT-07 — The site description document (IX-6) and the link relations of every page head.
  • CT-08 — Exported service records (NG-7): proposals, reviews, audit as JSON Lines.

5. Operational behaviours (OP-…)

  • OP-01 — Writes are serialized per wiki by a lease; a second acceptance waits a bounded time, then busy with a wait estimate (PERF-2).
  • OP-02 — The honesty line is everywhere (RD-4): a stale cache never serves a verification badge; an unverified repository shows it and refuses acceptances (INT-6).
  • OP-03 — Degrade safely: if prikk is unavailable for a wiki, reads serve the cache labelled stale, writes refuse with a reason; nothing is invented.
  • OP-04 — Bounded: page, proposal and attachment sizes (PERF-4); prikk calls under a budget (SEC-7); imports bounded and dry-runnable.
  • OP-05 — Formats: the serving binary stays at or above each repository’s prikk format; upgrades are the operator’s act (DUR-3).
  • OP-06 — Verification cadence: after every seal and on a schedule; results recorded per wiki.
  • OP-07 — Keys at rest: encrypted under the operator’s secret; decrypted only for a write, onto a private mount visible to the sandboxed prikk and removed after (SEC-4).

The essence, in one paragraph. inklkunn differs from planeter on the axis that matters most: it holds history-signing keys. By the owner’s ruling (DR-4) the wiki service is the author and the maintainer of its own repositories, because wiki contributors hold no keys and must not need to. So the central property of a prikk forge, “a compromised service can deny history but never forge it”, does not hold for inklkunn as a whole; what inklkunn offers instead is that a forged change is detectable and attributable: every signature is the wiki service’s and says so, every change names the proposal and the people behind it in a signed message, planeter can hold the same repository read-only as an independent witness, and the keys live behind a boundary no web request can cross. The second signature danger is the familiar one: a service that renders and stores text from strangers, faces the network, and serves mutually distrusting users inherits every web threat a wiki has ever had, plus the social ones a wiki’s thesis invites, since the same low friction that makes participation inclusive makes abuse cheap (register item 7). The modern addition is AI in the loop, answered by keeping content as data and keeping any AI out of the authority path. The design consequence that follows is the signer boundary (TB-5, INV-2): keys reachable from one component only, that component reachable from the web tier through one narrow call, and the whole arrangement a property of the build graph.

1. Assets (A-…)

  • A-HISTORY — the integrity and prikk-verifiability of each wiki’s history. Its value: anyone holding the repository can prikk verify it offline and read who accepted what.
  • A-KEYS — the per-wiki author and maintainer keys. The highest-value secret: whoever holds a wiki’s maintainer key can seal history that prikk accepts.
  • A-ATTRIBUTION — the truth of “who proposed, who accepted”: in the signed patch message and in the service records, cross-checkable.
  • A-AUTHZ — roles, policy, protections; corruption grants writes or reads to the wrong people.
  • A-CREDS — passwords, sessions, tokens.
  • A-CONTENT — private wikis’ pages and proposals; held-for-review content that is not yet public.
  • A-RECORD — the service store: review state, audit log; and the derived cache, whose corruption could mislead a page.
  • A-HOST, A-AVAILABILITY, A-SUPPLY — as for any service.
  • A-COMMUNITY — the social system’s health: a wiki captured by a faction or buried in spam is as lost as a corrupted one (register item 7, 12 of the main transcript).

3. Threats and controls (T-…, C-…)

T-1 — Forged history: a change sealed without an authorized acceptance

The maintainer key is used by something other than FL-04’s acceptance: a compromised web tier calling the signer directly, a stolen key, an insider with the key store secret, a bug that seals without a proposal. (A-HISTORY, A-KEYS, A-ATTRIBUTION.)

  • C-1a — The signer is the only holder and the only user of keys (TB-5; INV-2). Key material is loaded by the signer component alone; the web and API tiers depend on an interface whose one operation is accept this prepared change for this proposal and whose result is the sealed change’s ids. A build gate fails if any other crate depends on the key store.
  • C-1b — Every seal is bound to a recorded proposal and acceptance. The signer refuses a change that names no proposal in an accepted-pending-seal state with an intent record; the patch message (CT-03) carries the proposal id and the acceptor; the acceptance record carries the block and patch ids. A seal that matches no acceptance record is detectable by a reconciliation that runs after every seal and on a schedule, and is reported, never hidden.
  • C-1c — Keys at rest are encrypted under the operator’s secret, decrypted for one write onto a private mount only the sandboxed prikk can read, removed after; never logged, never in content, never exported (SEC-4, OP-07). The secret is supplied at start, not stored beside the keys.
  • C-1d — Per-wiki keys and rotation. A compromise is bounded to one wiki; rotation adopts a new key id and removes the old from the repository’s trust store; the procedure is documented and rehearsed.
  • C-1e — Independent witness. The repository can be hosted read-only by planeter and exported as an archive at any time (MD-5, IX-2), so a forged change is visible to a path the wiki does not control.
  • C-1f — Honest labels. Every change is labelled signed by the wiki service on behalf of … (ID-5): the reader is never told a person signed.

T-2 — Authentication and session attacks

Credential stuffing, session theft, OpenID Connect misconfiguration, token leakage (A-CREDS).

  • C-2a Argon2id passwords; OpenID Connect with PKCE, one-shot state, nonce-bound tokens verified against the provider’s keys; constant-work sign-in so account existence does not leak by timing (planeter’s IS-31 lesson, adopted from the start).
  • C-2b Per-account and per-client-IP throttles; the client IP only from a declared trusted proxy.
  • C-2c Secure, HttpOnly, SameSite cookies; CSRF double-submit on every cookie write; scoped, hashed, expiring, revocable tokens; re-authentication for key operations and role grants.
  • C-2d A second factor is a stated gap for v1 (RR-4); an OpenID Connect provider that enforces it is the interim answer.

T-3 — Authorization bypass and confused deputy

A reader reaches a private wiki, a proposer accepts their own proposal, a token with read proposes, a role is escalated through a policy edit (A-AUTHZ, A-CONTENT).

  • C-3a One pure default-deny authorize() on every path (ID-7); a test enumerates every route and verb and asserts the call (planeter’s ENF-4, written before the first write handler).
  • C-3b Scopes intersected with roles per endpoint; existence-neutral denials.
  • C-3c Policy changes are proposals under the constitutional layers (GV-1); the bootstrap roles cannot be removed by a policy edit; protections are authorization outcomes, not UI.

T-4 — Hostile proposed content

Attacker-controlled text that becomes a file in a repository: a title that is a path (../, reserved names, case collisions), frontmatter that is YAML with surprises, a body that is a bomb, an attachment that lies about its type, a rename to a path outside pages/ (TB-3; A-HOST, A-HISTORY).

  • C-4a Title-to-path mapping is a pure, documented, fuzz-tested function that refuses anything not a safe relative component under the wiki’s directories (CT-01); the repository root and .prikk/ are never a destination; prikk’s own path safety is the second line, never the first.
  • C-4b Frontmatter is parsed with a plain YAML subset (scalars, lists, maps; no anchors, no tags) and validated against the metadata schema; unknown keys preserved as data; secrets and control fields (visibility, kind: system) are set by the service, not by the proposer, unless the role allows.
  • C-4c Sizes bounded before parsing (PERF-4); attachments type-checked by content, served as attachments from the content origin; SVG sanitized or served inert.
  • C-4d Pasted and proposed Markdown is data; no directive executes (NG-8); raw HTML reduced to the documented subset.

T-5 — Hostile imports (TB-10)

Archive traversal, symbolic links, deep nesting, size bombs, a bundle whose manifest lies, a prikk archive carrying keys to adopt.

  • C-5a Imports are admin-only, dry-run first, bounded, extracted into a private scratch directory with every entry’s path validated; symbolic links refused; checksums verified when present (wiki-commons SEC-7).
  • C-5b A prikk archive import never adopts carried keys; the wiki’s own keys remain the only trusted signers (prikk’s own rule: carried, not adopted).
  • C-5c Imported content goes through the same sanitizer and the same path mapping as a proposal, and arrives as attributed changes with an import report (IX-3).

T-6 — Cross-site scripting through rendered content (TB-7)

  • C-6a Strict CSP, no inline script, no third-party scripts; nosniff, frame-ancestors 'none', Referrer-Policy.
  • C-6b Allowlist sanitizer on every render, including previews and diffs (a diff renders attacker text twice).
  • C-6c Raw source, attachments and downloads only from the isolated content origin, as inert attachments; the host gate enforced, not only configured (planeter’s IS-16 lesson).

T-7 — Confidentiality of private wikis and held content

  • C-7a authorize() on reads, feeds, search, backlinks, sitemaps, link previews and the API; noindex; existence-neutral errors (PRV-4).
  • C-7b Held-for-review content is visible only to those the policy names; notifications never carry content the recipient could not read (PRV-5).
  • C-7c Secrets committed into pages are carried by prikk and cannot be un-leaked; the risk is stated to operators (SEC-9; RR-2).

T-8 — Server-side request forgery (TB-6)

  • C-8 One egress guard for every outbound fetch (SEC-6): public unicast only, pinned addresses, HTTPS only, no redirects followed blindly; link previews and interwiki checks are click-to-load or server-side through the guard; webhooks the same when they come.

T-9 — Denial of service

Expensive prikk calls on large repositories, proposal floods, huge pages, acceptance queues, import bombs (A-AVAILABILITY, A-HOST).

  • C-9a Every prikk call under a time and memory budget with weighted admission and a per-call ceiling (SEC-7; planeter RFC 011 pattern); a ceiling hit is unavailable, never a verification verdict.
  • C-9b Quotas per principal and per wiki (PR-14); rate limits with Retry-After; bounded page and attachment sizes; the acceptance queue bounded and visible.
  • C-9c Metering and alerts on disk (repositories only grow; prikk deletes nothing) and on queue depth.

T-10 — The service store or the cache as a false source of truth

A corrupted record or cache shows a page that is not the history, or marks a proposal accepted that was not sealed (A-RECORD, A-HISTORY).

  • C-10a The repository is the source of truth for content and history; the cache is keyed by prikk’s content ids and rebuilt from prikk; a verification badge is never served from a cache (RD-4, CM-7).
  • C-10b The reconciliation of C-1b runs both ways: every acceptance record names a block that exists and verifies; every sealed block names an acceptance record; disagreement is reported.
  • C-10c A test rebuilds every view with the derived store cleared and compares (CM-7).

T-11 — Supply chain

  • C-11 Pinned and locked dependencies, cargo deny and cargo audit at every project event, a license allow-list, forbid(unsafe_code), measured growth, a preference for confined subprocesses over in-process protocol stacks (planeter’s dependency policy, adopted); CI actions pinned by digest.

T-12 — Repudiation

“I never proposed that”, “I never accepted that” (A-ATTRIBUTION).

  • C-12a The signed patch message names the proposal, the proposer and the acceptor (CT-03); the service records hold the same with timestamps; the audit log is append-only and exportable (ID-8).
  • C-12b The limit is stated: prikk’s signature proves the wiki service signed, not the person; the person’s act is proven by the service’s records and the audit log, which the operator controls (RR-1).

T-13 — The AI-era surface

Prompt injection through page text against any future assistant; AI-scaled proposal spam; dependency hallucination in the build (A-CONTENT, A-COMMUNITY, A-SUPPLY).

  • C-13a No AI holds authority: nothing can propose, accept, moderate or change policy autonomously; any assistance is advisory, labelled, attributed to the human who accepted it (NG-5; C-13; AUTH-14).
  • C-13b Content is data, never instructions, for inklkunn and for any integration it hosts.
  • C-13c No private content leaves to an external AI without explicit per-use opt-in.
  • C-13d AI-scaled abuse is bounded like any abuse: quotas, the ladder, review before acceptance, and the inclusiveness metrics that show concentration and flood.

T-14 — Abuse of the social system

Astroturfing, brigading, sock puppets, source flooding, citation laundering, harassment dressed as epistemic discussion, strategic forks, capture of the maintainer role (register item 7; A-COMMUNITY).

  • C-14a Every consequential act is attributed, logged and visible: who proposed, reviewed, accepted, moderated, changed policy (PR-12, GV-3).
  • C-14b Soft security first, then progressive friction set by policy: quotas, new-account limits, protections per page, review required (GV-4, GV-7).
  • C-14c Moderation hides with a tombstone and an appeal; nothing is erased silently (GV-5, GV-8).
  • C-14d The constitutional layers keep the root roles out of reach of a captured policy (GV-1); no opaque reputation becomes a lever for capture (GV-2).
  • C-14e The inclusiveness metrics expose concentration and silence (GV-9).

T-15 — Removal, privacy and the immutable record

Personal data, defamation, infringing or illegal content in a sealed change; a person’s right to be forgotten (register item 14; A-CONTENT).

  • C-15a Suppression on the view is immediate: the content, summary or author of a revision hidden behind a tombstone with a reason, logged, reversible (GV-5, HIST-12).
  • C-15b Permanent removal is a documented operator procedure that states its cost: prikk cannot delete an object, so the repository is re-created without the content and the ids of affected history change; the procedure exists and is rehearsed before any public deployment (GV-6).
  • C-15c Pseudonymous participation, no published addresses, account deletion replaces the name with a stable pseudonym (PRV-2, PRV-3).

T-16 — The planeter boundary (TB-9)

A forged identity assertion from a fake planeter; planeter’s guarantees weakened by inklkunn.

  • C-16a Identity assertions are verified cryptographically (OpenID Connect tokens or signed tokens per RFC 008), never trusted from a header alone except behind a declared trusted proxy.
  • C-16b inklkunn never gives planeter a key, never writes to a planeter-hosted software repository, and planeter never writes to a wiki repository (MD-1, MD-5).

4. Security invariants (INV-…) — a change that breaks one is a security bug

  • INV-1 — No history without an authorized acceptance. Every sealed change names a recorded proposal and acceptance; the reconciliation detects any other.
  • INV-2 — Keys are reachable from the signer alone. No web, API or storage-read code path can read key material; the build graph enforces it; keys are encrypted at rest and never leave the host unencrypted.
  • INV-3 — All network input is untrusted; no content-provided code executes; the prikk parser runs confined; every user-influenced URL is SSRF-filtered.
  • INV-4 — Authorization is default-deny on every access path, enforced by one function and one test.
  • INV-5 — prikk is the source of truth; the service store and the cache are never authoritative for history; a verification badge is never served stale.
  • INV-6 — Honesty of labels: nothing says verified unless prikk verified it just now; nothing implies a person signed cryptographically; held-for-review content is never shown as the record.
  • INV-7 — Content is data, never instructions; no AI holds authority.
  • INV-8 — Removal is suppression plus a documented procedure, never a silent rewrite.
  • INV-9 — The supply chain is pinned, minimized and audited; every crate forbids unsafe code.
  • INV-10 — Attribution survives either store: the signed message and the service records agree, and disagreement is reported.

5. Residual risks and assumptions (RR-…, ASSUME-…)

  • RR-1 — The service holds the keys. A total compromise of the host or of the key-store secret lets an attacker seal history that prikk accepts, in every wiki whose keys they obtained. The ruling DR-4 accepts this for the sake of keyless participation; the controls make it bounded (per-wiki keys), detectable (reconciliation, independent witness), attributable (every seal says it is the service’s) and recoverable (rotation). This is the central difference from planeter and must be said plainly in SECURITY.md.
  • RR-2 — Secrets committed into pages are carried faithfully; rotation in the real world is the only remedy.
  • RR-3 — The prikk subprocess parses attacker-influenced bytes (paths, content, imported archives); a prikk parser fault is confined, not eliminated.
  • RR-4 — No second factor in v1 on local accounts; an OpenID Connect provider that enforces one is the interim answer.
  • RR-5 — Social capture is bounded, not prevented. A faction holding the admin role can govern badly in the open; the model makes it visible and forkable, not impossible.
  • RR-6 — Removal is lossy. A legal removal changes the ids of affected history and breaks permalinks; the procedure says so.
  • RR-7 — Throttles and leases are per process in v1; a multi-replica deployment needs the proxy to throttle and a shared lease (operations RFC before 1.0).
  • ASSUME-1 The operator and the host are trusted; inklkunn defends against network actors and malicious users, not a hostile operator.
  • ASSUME-2 prikk’s offline verify is correct and is the arbiter of history integrity.
  • ASSUME-3 planeter, when integrated, enforces its own invariants; inklkunn does not rely on planeter for any of its own.

2. Layering and boundary rules (LAY-…) — enforced, not drawn

  • LAY-1 — Downward only. upper → core → lower. A production dependency from a lower or core crate into an upper crate fails boundary-check, naming the edge (planeter’s gate, adopted).
  • LAY-2 — authorize() lives in CR-core and every surface calls it (INV-4). A route-enumeration test in CR-web asserts every registered route and API verb either consults it or is registered public with a reason (planeter’s ENF-4), from the first write handler.
  • LAY-3 — Only CR-prikk and CR-signer spawn prikk; CR-signer only for writes, CR-prikk only for reads; a source gate fails on prikk invocation anywhere else.
  • LAY-4 — Only CR-signer depends on the key store (INV-2). The key store is a module inside CR-signer with no public export of key bytes; boundary-check fails if any other crate declares a dependency on CR-signer’s internals or names its key-store module, and a test asserts CR-web’s dependency closure contains the signer trait crate only through CR-core.
  • LAY-5 — One egress guard in CR-core for every outbound fetch (INV-3).
  • LAY-6 — CR-markup is pure. No I/O, no clock, no randomness; boundary-check fails on an I/O dependency.

3. The storage driver (STO-…) — CR-prikk

  • STO-1 — The Storage trait names what inklkunn needs of a repository, in inklkunn’s words: list views and their tips; the tree at a point; a file’s bytes at a point; the history of a view; one change’s content; a diff between two points; materialize a point into a scratch directory; verify. Points are view names or block ids. The trait is the seam for a future library or another backend (UD-2).
  • STO-2 — The first implementation drives the prikk CLI: branch --format json, tree, cat, log, show, diff, extract, verify, each parsed into typed values; the schema_version of every report is checked against the pinned set and an unknown one is a typed refusal (INT-1). The floor (0.54.0) is one constant checked by floor-check against the CI image and the release notes.
  • STO-3 — Sandbox. Every call runs under bubblewrap (--unshare-all, --clearenv, --die-with-parent), a read-only system view, the repository directory and the call’s scratch directory mounted, a wall-time bound kept by the server, and a prlimit data ceiling from a per-verb cost table measured on the floor (planeter RFC 011’s shape, with the table re-measured at each re-baseline).
  • STO-4 — Admission. A gate with a memory budget split into a light pool (floor-cost reads: branch, log paged) and a heavy pool (extract, verify, diff on large points); refusals are busy or too_large, never silence.
  • STO-5 — Reads never take a write lock; prikk’s read verbs create no lock files, and the driver never invokes a verb that does.

4. The signer (SGN-…) — CR-signer

  • SGN-1 — The key store. One record per wiki: the author and maintainer seeds encrypted with a key derived from the operator’s secret (supplied at start through the environment or a file, never stored with the records), the key ids, the created and rotated-at times. Decryption yields seed files written to a private, mode-0600, tmpfs-backed directory mounted into the sandbox for one write call and removed after (OP-07).
  • SGN-2 — Key operations: create (prikk key generate twice, trust maintainer add in the wiki’s repository, record), rotate (new ids, adopt, remove the old from trust, record), status (ids and dates only). Each is an audited admin act (ID-8).
  • SGN-3 — The one way in. A trait Accept with one operation: given a wiki, a view, an acceptance token (the id of an acceptance record in state pending seal, with its intent) and a prepared change (the files to write, renames, the CT-03 message), bring the worktree to the view, apply, mv, commit under the author key, seal under the maintainer key, verify, and return the sealed change’s block and patch ids. It refuses a change whose acceptance record is not pending or whose message does not name it (C-1b). It never exposes a key, a seed path or a signing primitive.
  • SGN-4 — Branch creation for a new view is the signer’s second operation (a maintainer-signed publication in prikk), bound to a recorded view-creation act.
  • SGN-5 — Process separation is a documented option, not v1: the trait is designed so CR-signer can run as a separate process on a local socket later (threat model RR-1), with no change to callers.

5. Markup (MK-…) — CR-markup

  • MK-1 — Parse CommonMark + GFM extensions + footnotes with a conformant parser (pulldown-cmark, the house choice), then the profile’s Layer 2 on top: free links in every form of MKUP-4, embeds, block identifiers, inline tags, callouts, hidden comments, the interwiki prefix form, generic directives, and the snapshot envelope recognized as a container.
  • MK-2 — Frontmatter in the plain YAML subset (C-4b), validated against the metadata vocabulary; unknown keys preserved; kind, visibility and system keys writable only by the service.
  • MK-3 — Resolve links by the MKUP-5 order against a view’s title index (titles, aliases, redirects, normalization, hierarchy fallback), producing resolved, dangling and interwiki link sets and the backlink edges.
  • MK-4 — Render to a semantic HTML tree with the MKUP-12 conventions, then through the sanitizer in CR-web; headings get deterministic ids; identified blocks get id attributes; dangling links get the marker and the accessible description.
  • MK-5 — Blocks. Every top-level block gets a stable address: the ^id if present, else a derived address used only transiently (anchors that must persist are given a ^id by the acceptance that attaches something to them, CM-5).
  • MK-6 — Lint produces suggestions with the guideline they come from (AUTH-13).
  • MK-7 — Title ↔ path (CT-01): a pure function and its inverse under test and fuzz: NFC, the forbidden characters replaced by a documented substitute, / as hierarchy, case-collision suffixes, reserved names refused, never escaping pages/.

6. Data model (DM-…)

  • DM-1 — Wiki record: opaque id → on-disk path (<root>/<shard>/<wiki id>/.prikk), display name, slug for URLs, default view, default license, languages, visibility, policy bootstrap, prikk format version, verification state and time, key ids (never seeds).
  • DM-2 — Repository content is the bundle (CT-02); inklkunn reads it through STO and writes it through SGN; nothing of inklkunn’s lives in .prikk/.
  • DM-3 — Proposal, revision, comment, decision, intent, acceptance as CT-04, append-only where the threat model needs it (decisions and acceptances are never updated, only added); ids are UUID v7.
  • DM-4 — Accounts, identities, roles: account {id, display name, status}, identity {account, kind: local | oidc(issuer, subject)}, role grant {account, wiki, role, granted by, at}, token {account, scopes, hash, expiry}.
  • DM-5 — Audit log {at, principal, action, resource, outcome, detail without content}.
  • DM-6 — Derived cache {wiki, view tip block id, page id or path, catalog language, rendered HTML, link sets, computed at}; invalidated by view tip; never holds a verification result.
  • DM-7 — Title index per view tip: title, aliases, redirect targets, page id, path — derived from the frontmatter of all pages at that tip, cached, rebuilt on tip change.

7. The read path (RD-…)

  • RD-1 Resolve the wiki by slug → authorize(principal, read, wiki) → the view (default unless named) → its tip from branch (cached briefly) → the title index at that tip (DM-7) → the page path → the cache by (tip, path, language); on a miss, cat the file at the tip, parse (MK-1 … MK-4), resolve against the index, render, store.
  • RD-2 History from log of the view (paged) and show of a block; diffs from diff --from --to restricted to the page’s path, rendered word-level in inklkunn from prikk’s hunks (prikk supplies the line diff; the word-level refinement is a presentation step and is labelled as inklkunn’s).
  • RD-3 The verification badge from the wiki record’s last verify (OP-06), re-run on demand when the page is the verification page itself; never from DM-6.
  • RD-4 Search: SQLite FTS5 over titles, aliases and (from M2) bodies at the default view’s tip, with a trigram tokenizer for scripts without word delimiters; rebuilt on tip change incrementally by changed paths (from diff).
  • RD-5 Feeds and recent changes from log across the wiki’s views, filtered by authorize().

8. The write path (WR-…) — the centerpiece

  • WR-1 — Propose. CR-core records the proposal and its first revision (DM-3) with the base block id of the target view’s tip at that moment and the proposed content per page; drafts are revisions in state draft; nothing touches prikk.
  • WR-2 — Review adds comments and decisions bound to the revision (DM-3); a new revision clears the decisions’ applicability (they stay recorded, shown as “on revision N”).
  • WR-3 — Accept. authorize(principal, accept, proposal) (policy: role, required approvals, protection) → take the wiki’s lease (CON-1) → re-read the view’s tip → if the tip equals the base, the change is the proposal’s content; else MRG-1 per page → on an unresolved overlap release the lease and move the proposal to needs a revision with both texts recorded → else write the acceptance record (pending seal) and the intent (CON-3) → call Accept::accept on the signer (SGN-3) → on success record the block and patch ids, mark accepted, complete the intent, invalidate DM-6 and DM-7 for the view, enqueue the verification (OP-06) and the notifications → release the lease.
  • WR-4 — Failure before the seal (merge, write, commit refused): nothing in prikk changed; the acceptance record is marked failed with the reason; the proposal stays open.
  • WR-5 — Failure after commit but before or during seal, or a crash anywhere: the intent is open; the wiki is flagged needs recovery and refuses writes (CON-4) until the recovery completes the seal (prikk’s own queued patch is sealed by the recovery’s seal, or discarded by doctor --discard-damaged-commits when its witness is damaged) and reconciles the acceptance record.
  • WR-6 — The message (CT-03) is composed by CR-core and checked by the signer against the acceptance record before it signs anything (C-1b).
  • WR-7 — Import is a sequence of acceptances under a system principal with Kind: import and the import report’s provenance, in batches bounded by the budget.
  • WR-8 — New view (M3): a recorded view-creation act → SGN-4 → the view appears; proposals then target it like any other.

9. Content-level merge (MRG-…)

  • MRG-1 — Three-way, per page, per block. Base = the page at the proposal’s base block (cat); theirs = the page at the current tip; ours = the proposed page. Frontmatter merges key by key (a key changed on both sides with different values is an overlap). Bodies merge by a block-aware three-way diff: blocks are the units (MK-5), and within a changed block a line/word three-way merge is attempted; a block changed on both sides with no clean merge is an overlap.
  • MRG-2 — Overlap is never auto-resolved (INT-7, consistent with prikk). Both texts are stored on the proposal and shown side by side; the proposer or the acceptor revises.
  • MRG-3 — Renames and deletions merge by page id: a page renamed on one side and edited on the other merges (the edit lands on the renamed file); deleted on one side and edited on the other is an overlap.
  • MRG-4 — The spike (M0, roadmap R2) measures, on a corpus of wiki-shaped edit histories, how often a moved base merges cleanly, how often prikk’s own span anchors would have survived, and the cost; its numbers calibrate PERF-2 and may simplify MRG-1 (if prikk’s EditText anchors survive most moved bases, the merge can be delegated to prikk’s commit against the new tip for the clean case).

10. Identity and authorization internals (AZ-…)

  • AZ-1 CR-auth produces a principal: anonymous, account (via session or token with scopes), or a system principal (import, recovery). OpenID Connect through the egress guard with a confined curl (planeter’s pattern) or an in-process client if the dependency policy permits one (IQ-3).
  • AZ-2 authorize(principal, action, resource) in CR-core: pure over a snapshot of roles, policy and the resource’s visibility; default deny; existence-neutral; audited for consequential actions (ID-8). Policy in M2 is the bootstrap’s fixed role set; M4 reads the versioned policy object (GV-1).
  • AZ-3 Scopes intersect roles (read ⊂ propose ⊂ review ⊂ accept ⊂ admin); protections evaluated inside authorize(_, accept | propose, page).

11. Concurrency, consistency and recovery (CON-…)

  • CON-1 — One write lease per wiki, in-process (an async mutex keyed by wiki id) in v1, with a durable holder record so a crashed holder is recognized at start; readers never wait for it.
  • CON-2 — prikk’s locks are the layer beneath: a lock conflict from prikk is reported, the acceptance fails before the seal (WR-4) or flags recovery after it (WR-5); no lock is ever cleared automatically.
  • CON-3 — The intent journal (DUR-2): written before the signer is called with the acceptance id, the wiki, the view, the base and the message digest; completed with the block id; a crash leaves it open.
  • CON-4 — Recovery at start and after a failed acceptance: read the witnesses (open intents, the lease record, prikk status, doctor, unlock listing, foreign processes), then under the lease: complete a queued commit by seal when the witness matches the intent, or discard it by doctor when it does not; unlock stale locks of the kinds an acceptance leaves; verify; reconcile acceptance records against blocks (C-10b); clear the flag. Every step recorded; the administration surface shows the plan (planeter RFC 004 part 4, adapted).
  • CON-5 — Cache coherence: DM-6 and DM-7 keyed by view tip; a tip change invalidates; a stale read is labelled when prikk is unavailable (OP-03).
  • CON-6 — Idempotence: an acceptance is keyed by the proposal revision; a retried accept finds the record and does not seal twice; an import is keyed by the bundle digest.

12. Invariant enforcement (ENF-…)

  • ENF-1 — INV-2: boundary-check asserts only CR-signer names the key-store module and only CR-core depends on CR-signer; a test instantiates CR-web’s dependency graph and asserts no path to key bytes.
  • ENF-2 — INV-1 / INV-10: the reconciliation runs in tests with a planted unrecorded seal and a planted unsealed acceptance and must report both.
  • ENF-3 — INV-4: the route-enumeration test (LAY-2), from the first write route.
  • ENF-4 — INV-3: the title-to-path fuzz; a hostile bundle fixture; an SSRF fixture per fetch site; the sanitizer’s regression tests.
  • ENF-5 — INV-5 / INV-6: the derived store is cleared and every view rebuilt and compared; a badge is never read from DM-6; an open proposal’s content is rendered only on its proposal page with the held-for-review label.
  • ENF-6 — INV-7 / INV-8: no crate exposes an authority path to an automated actor; the removal procedure is a documented, rehearsed runbook, not code that rewrites history.
  • ENF-7 — INV-9: cargo deny, cargo audit, pinned CI actions, forbid(unsafe_code) in every crate, the dependency ledger (planeter’s, adopted) with measured growth per manifest change.
