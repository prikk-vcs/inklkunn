## 2. What R-2 proves, in terms a reader of the product would use

Real prikk, a real key store, a real SQLite store, a real socket; the binary's own `prepare` with its own `Identify`, nothing replaced by a header-named test identity. Accounts come from the operator's `account invite` and the invitation page; sign-in is the sign-in page with a cookie jar that keeps a `__Host-` cookie only if it has `Secure`, `Path=/` and no `Domain`; every form is read off the page it came from (the hidden `csrf` field, the double-submit cookie, the same-site headers; menus, radio buttons and boxes are sent as a browser sends them). It is U6's harness, extended for menus and radio buttons; nothing was copied. The test is `serve::writes_on::tests::knowledge::the_knowledge_layer_works_end_to_end_on_a_real_prikk` (`crates/inklkunn/src/serve/writes_on/tests/knowledge.rs`). Four people take part: Noor (contributor), Quinn (reviewer), Maya (maintainer) and a visitor with no account.

- **A claim is made by a proposal and by nothing else.** Noor opens *Propose a change to a section or a part* on the *Help* page, chooses *Attach a source* on one paragraph and fills the source's form (what kind, title, author, date as written, a web address, how directly it speaks to the paragraph). While the proposal is held, a visitor's *Help* page has no claim link, the repository has not gained a block, and the proposal's own page says it records a claim and a source. A script's proposal that names a claim file is refused with `path-outside-pages` and records nothing. After Maya approves and accepts, one new block is in the history.
- **What a reader sees.** The visitor's *Help* page has exactly one new thing: *Sources and views*, on that one paragraph, and still exactly one *Why is this here?* link among the page's tools. The claim's page says what kind of statement it is (*an observation*), where it is said, the source with its title, author, date and address, *supports, directly*, and *This claim has not been decided in this view.* The API's `claims/{id}` names the same claim and source to the same visitor. None of the words *true*, *false*, *verified*, *proven*, *canonical*, *official*, *adopted* is used as a word on any of these pages (the paragraphs that *Why is this here?* quotes are the wiki's, not the product's).
- **Why is this here?** For the claim's paragraph: the latest change found, the earliest wording found, and the way on to the claim's page. For an ordinary paragraph: the earliest wording found and the label *Traced by matching the text*, with no link to a claim. For the change: who proposed it, who accepted it, the reviewer's approval with the words they wrote.
- **Views, and what differs.** A contributor is offered no form to create a view (403); Quinn creates *reading*, an interpretation view, and the list says what kind it is and what it was forked from, beside the default view. Until anything differs, the claim says *No other view reads this claim differently.* In the view: a paragraph is reworded, and the claim there reads *Judged on an earlier wording* (the default view's does not); one curation proposal with the confirmation box sets the status to *contested* and judges the source again on the new wording, and the note is gone (one step); a challenging source is added (*challenges, in part*). The default view still says *not decided* and one source. *Compare views* lists the claim as *worded differently*, *Its status: not decided in the default view, contested in the view “reading”*, *Its sources differ*, and the page as differing, with its own line-by-line diff and word marks.
- **Proposals written against one tip.** A status change, a second source and a different status change are written before any is accepted. The first is accepted; the second is accepted after it and is one new block, with the status the first made and both sources (the knowledge files merge key by key and no relation is lost); the third changes the status the first changed: *Stopped: changes overlap*, the proposal says it needs a revision, the repository has not gained a block and the status is still what the accepted proposal made it.
- **Freshness.** *Sources to review* first lists both sources as *No one has recorded looking at it.* A curation proposal records one source as looked at today and the other as looked at on 2022-03-01; once accepted the list names only the second, *Last reviewed on 2022-03-01, more than 1096 days ago*, with the one claim that relies on it, and does not list the first.
- **A claim's thread.** Noor and Quinn write two comments on the claim's page; the page shows them in order with their names, and markup in a comment is shown as letters. The claim's status is unchanged by them.
- **The export, and the bundle offered to another wiki.** With the server stopped, `wiki export` writes a bundle that changes nothing in the wiki. Its manifest validates against wiki-commons' bundle schema (the core's own checker and its copy of the schema) and declares `inklkunn-knowledge` in `extensions_used`; the claim file and both source files are in it with the fields the wiki holds (kind, expressions, relations, status, each source's relation, bearing and `judged_on`); the thread is one line per comment, bodies as fenced text, authors named; the views record names *reading*; the extension's files are in `SHA256SUMS`. Offered to a second wiki, the bundle is refused whole, by file and by rule, for the status, the review days and the availabilities it carries (an import brings no curated state; nothing is stripped), and with one claim file replaced by text that is not a claim, that file is refused by name; both times nothing was written.

## 3. The upgrade from 0.2.0 (R-3)

**The 0.2.0 binary.** The release asset of this project's GitHub release `0.2.0` (published 2026-11-04), fetched with
`gh release download 0.2.0 -R prikk-vcs/inklkunn -p 'inklkunn-x86_64-unknown-linux-gnu.tar.gz'`: 7,407,251 bytes, sha256
`e29814e026390ee8b46b744f862977efca53e5ec025af7ef8e11255b043bff86`, which equals the release's own `.sha256` file, the digest
GitHub's API records and a `sha256sum` made here. Its `--version` says commit `c6c7939c9d9c4ec4eb0982923a767c961c5e7053`. CI
installs it the way it installs the test-only prikk 0.57.0: `UPGRADE_FROM_VERSION` and `UPGRADE_FROM_SHA256_X86_64` are recorded in
`ci.yml` and `release.yml`, `sha256sum -c` runs before unpacking, the unpacked `--version` is checked, and `~/.local/inklkunn-old/bin`
goes on `PATH`; floor-check holds the two workflows' values equal and the step's shape. This tree's own binary also says
`inklkunn 0.2.0` until R-7 moves the version, so the test finds the old one **by its commit**.

**The test** (`crates/inklkunn/src/serve/writes_on/tests/upgrade.rs`, U6's harness): the 0.2.0 binary, as processes, creates a
wiki, two invitations and runs its own server; a maintainer and a contributor redeem and sign in; the contributor proposes two
edits and the maintainer accepts one; the server is stopped (exit 0) and the store's schema is read: **15**. This tree's `prepare`
then opens the directory: the signer opens over 0.2.0's key store, the schema is **18**, the history is the two blocks 0.2.0
wrote, the page shows the accepted wording and not the open proposal's, **both accounts sign in with the passwords chosen in
0.2.0**, the maintainer accepts the open proposal (one new block; the page holds both changes; it was authored against the
history before the accepted change, so this is also the re-authoring path on a migrated store), and no secret is in either
half's output. Mutations that killed it: the schema version not recorded (the store is refused), migrations skipped (the
accept answers 503), a catalog line changed (the D-7 comparison fails), one stylesheet line changed (the stylesheet
comparison fails); **not mutated one by one:** sign-in of the migrated accounts, the signer opening over the old key store, the
secret scan.

**By hand**, once, 0.2.0's binary and this tree's debug binary on the same directory (both `--dev-unconfined`, because the
0.2.0 binary cannot confine on this host class: IS-19): schema 15, then 18; the signer open over `data/keys`; the two servers exit
0; *Help* and *About* answer 200. The test's run on this tree with the checksum-checked binary (prikk 0.55.0 first, then
0.57.0) is in section 1.

**D-7 against 0.2.0's own output.** The 0.2.0 process and this tree answered the same directory, and 14 anonymous paths were compared:
**13 pages by status and body** (`/handbook/Help`, the same page at a block, `/handbook/-/history/Help`, `…/change/<block>`,
`…/changes`, `…/about`, `…/health`, `…/search`, `…/verification`, `…/discussion/Help`, `…/proposals`, `/-/wikis`, `/-/sign-in`) and **`/handbook` by
status and `Location`** (a 303 to `/handbook/-/about` in both; no *Home* page exists), which the first run of the test did not
compare (its body is only a redirect) and now does, with a mutation of the redirect that fails it. Masked first: the two servers'
ports, the stylesheet's hashed name and each form's csrf token. The pages are **byte-identical after taking out the three
things 0.3.0 adds, each asserted exactly** (so a second link, or a link on another page, shows as a difference): the one
`<p><a href="/handbook/-/why/Help">Why is this here?</a></p>` on *Help* (not on a block, the history or a change page), the
*All views of this wiki* link on *About*, and the *Sources to review* entry in the health index. **Excluded** (not compared): signed-in
pages, proposal pages themselves (the list is compared), Japanese pages, error pages and 404s, the content origin, every response
header except that `Location`, any page that holds a claim, a view or a thread (D-7 is about a wiki with none), other pages of
the wiki and any other wiki. **The style sheet is not 0.2.0's byte for byte:** every line of 0.2.0's is in this tree's, in order,
with additions between and one changed rule, `code { … overflow-wrap: anywhere; }` (K32), which applies to every `<code>` on every
page, claims or not. K-T6's CHANGELOG sentence said *a page with no claims is the page it was, byte for byte*; it now says *its
HTML*, and this section is where the exception is written.

## 6. Deferred, and why

| What | Why it is not in 0.3.0 |
|---|---|
| Removing or retiring a claim or a source; replacing a file that cannot be read | RFC 006 (0.4.0); ruled 2026-11-14; every surface says so plainly |
| Attaching an existing source to another claim | After 0.3.0 (a recorded gap): a new source works, and the cost is a duplicate file, not a wrong one |
| Reading threads and view records back on import | RFC 007 (M5); export carries them, so nothing is lost |
| IS-18: a restricted wiki's raw source when the content origin has its own host | RFC 006; it fails closed (*not found*), and the page itself reads (RR-14) |
