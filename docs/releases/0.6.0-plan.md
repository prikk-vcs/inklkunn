## 1. In one paragraph

**0.6.0 makes inklkunn something an operator can run and keep: imported pages show their images, a server is backed up
and restored as one set, and it says how it is doing.**
- **Attachments are served for the first time,** on the content origin. Until now no release served one, so an imported
  page's images do not show.
- **Backup and a rehearsed restore** of the whole authoritative set: the repositories, the service store and the key
  store, together and at one moment.
- **An operator can see the server's state:** a health answer that means something, a status command, logs that carry
  no content, and counters.
- **A deployment guide:** the proxy, TLS, the content origin's host, and the container.
- **The permanent removal procedure is 0.7.0, by itself (P-1).** It still comes before any public deployment.
- **The scope is frozen when you authorize this plan.**

**In 0.6.0** (two RFCs: 011, attachments and the content origin; 012, operations):

| | What | Requirement |
|---|---|---|
| a | **Attachments served, on the content origin** (RFC 011). The bytes come **through the one reader**, so what moderation hides is never served. **Every served attachment can be taken down** (*refined*): a proposal may **remove** an attachment and its sidecar (removal only; still no upload, P-4), and a moderator's hide applies to an attachment's content **even when it is the tip's**, served then as a tombstone in its place. Today a proposal refuses every path outside `pages/`, and the tip rule refuses the hide, so an imported image could be stopped by no one. Each is served with its media type from an allowlist, `nosniff`, and a download disposition for anything that is not a plain image. **SVG is served inert** (C-4c). An image embed resolves to its address, and the app's CSP names the content origin for images and nothing more. A small page on the app origin per attachment shows its licence and attribution from the sidecar | WEB-10, SEC-2, C-4c, C-6c, wiki-commons LIC-4 |
| b | **Restricted wikis on a content origin with its own host** (IS-18): short-lived addresses signed by the server for the reader who may read, so raw source and attachments work there too. A wiki that is not restricted needs no signature | RR-14, IS-18 |
| c | **Backup:** `inklkunn backup --to <file or ->`. One set, taken at one moment (every wiki's write lease held while the store is copied): each repository as prikk's verified archive, the service store, and the key store's sealed records, **never the secret file**, with a manifest of checksums, as **one archive** (*refined*):
- written to a file, owner-readable only, or to standard output, so that it can be piped to an encryptor and no unencrypted copy is ever on disk;
- **the command says in one line that the set is not encrypted, and that it holds people's data and what moderation hides**;
- **it never migrates the store** (*refined*): it reads a store of an older schema as it is, so *back up first* works with the new binary before an upgrade.

It does not stop reads | DUR-1 |
| d | **Restore:** `inklkunn restore <backup> <empty data dir>`. It checks the set, restores it, and runs `prikk verify` on every repository; **anything that does not verify refuses the restore**. **Rehearsed by a test:** backup, then restore elsewhere, then the same pages, accounts that sign in, and writes that work | DUR-1, DUR-4 |
| e | **Observability:** `/-/health` checks the store, prikk and the signer (public: *ok* or *degraded*, nothing more); `inklkunn status` lists every wiki's prikk format, verification state, flag and queue; **a wiki whose key store is missing says exactly that** (*refined*): in `status`, as *degraded* health, and in its refusal of a write, naming the backup to restore, never a general error (P-3); logs become structured lines (level, event, wiki id), and a test holds that no content and no secret reaches them; counters for admissions, refusals, acceptances and the background queue, kept in the process and printed by `status` | OPS-3, OPS-6 |
| f | **The deployment guide:** a part of the book for operators. It covers the reverse proxy and TLS, the two hosts (application and content), the container and a service unit, the data directory's layout, backup and restore, and upgrading. **Its first lines say who it is for** (*refined*): evaluation and private deployments, and what a **public** deployment still waits for (the permanent removal procedure, 0.7.0; the assistive-technology test; an external security review). A guide that says *deployment* must not read as *ready to deploy publicly* | OPS-5, OPS-2 |
| g | **Small items, run now as one maintenance package** (R-0): planeter 0.9.0's re-baseline (released 2026-11-24); prikk 0.59.0's if it is released in the cycle; the five 0.5.0 terms marked as ruled in the glossary; the proposal windows' indexes (W-9), **created when the store is opened, with no schema version change** (*refined*). The store checks its version, not its indexes, so 0.5.0 still opens a store 0.6.0 has opened, and 0.6.0 has no migration at all; the import notice on an imported page's own view; **Trusted Publishing in `release.yml`** once you say crates.io is set up | RFC 010 |

| Native Unicode paths; the planeter module | their own decisions | As recorded |

## 3. Your decisions in this plan

- **P-1 — The permanent removal procedure is 0.7.0, alone.** It keeps its deadline: before any public deployment.
  The deployment guide says so in its first lines (2f). **Recommended.**
- **P-2 — The backup is one archive the operator encrypts with their own tool,** piped from standard output so that no
  unencrypted copy need touch a disk (2c). It never contains the secret file,
  and the key records in it are sealed. The guide shows one way. DUR-1's *encrypted* then reads *encrypted at rest by
  the operator*. **Recommended.**
  - **The alternative:** inklkunn encrypts the set itself. That needs a new dependency and a second key to keep, and
    losing that key loses every backup.
- **P-3 — IS-15's re-keying waits for prikk's trust round.** Until then a missing key store is said plainly, with the way
  back (2e). **Recommended.**
- **P-4 — No attachment upload in 0.6.0.** Attachments arrive by import and are served, and **every served one can be taken
  down** (2a). **Recommended.**
- **P-5 — The small items (2g) run now,** as one maintenance package, while RFCs 011 and 012 are written.
  **Recommended.** Trusted Publishing waits for your word that crates.io is set up.

The RFCs bring their own questions. These are expected:
- the signed address's lifetime and what it binds (011);
- which media types are served inline (011);
- whether a backup holds the server briefly at one moment or waits for each wiki in turn (012);
- what `/-/health` may say to anyone (012).

## 4. Exit criteria (all must hold on the candidate commit)

1. **Gates green on the candidate:**
   - the architect's gates;
   - CI;
   - the release rehearsal;
   - the 0.54.0 floor over the whole workspace.
2. **Threat model v0.6** covers what 0.6.0 adds, and its §7 tests are re-verified on the candidate. It covers:
   - a hostile attachment (a script in an SVG, HTML named as an image, a media type that lies);
   - a signed address leaked, replayed or stretched;
   - a backup taken or read by the wrong person;
   - a restore of a set that was tampered with;
   - a health answer or a log that says too much.
3. **The readiness report,** reviewed by the architect, with every RFC criterion shown by a named test.
4. **The end-to-end proof on a real prikk:**
   - a BookStack import whose page shows its image, served from the content origin, with its licence page;
   - a restricted wiki's image through a signed address, and refused without one, after expiry, and for another path;
   - a hidden attachment never served;
   - a served attachment taken down by a proposal and by a hide at the tip;
   - a backup piped through an encryptor and back, a restore into an empty directory, every repository verified, and the wiki working;
   - a tampered set refused;
   - `status` and `/-/health` telling a degraded server from a healthy one.
5. **No open High issue.**
6. **An upgrade from 0.5.0 is shown,** against its release binary. There is no migration: the 0.5.0 binary still opens the store afterwards. A backup taken with the new binary before the first start is shown.
7. **The release notes' lead,** in a reader's words, with what 0.6.0 does not do.
8. **You review the Japanese** added or changed in the cycle, and **you authorize the cut.**
