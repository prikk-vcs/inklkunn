## 2. What U6 proves, in terms a reader of the product would use

Real prikk, a real key store, a real SQLite store, a real socket; the binary's own `prepare` with its own `Identify` — no
header-named test identity. Accounts come from the operator's `account invite` and the invitation page; sign-in is the
sign-in page with a cookie jar that keeps a `__Host-` cookie only if it has `Secure`, `Path=/` and no `Domain`; every form is
read off the page it came from (the hidden `csrf` field, the double-submit cookie, the same-site headers; a text area is sent
with CR LF as a browser sends it).

- **Sign-in and sessions.** The invitation link works once and is then the same page as one that never existed. A wrong
  password and a forged double-submit token are refused and set no session. The session cookie is `Secure`, `HttpOnly`,
  `SameSite=Strict`, `Path=/`, `__Host-`; the double-submit cookie is spent by the sign-in; a session that was ended is no
  session.
- **CSRF.** A forged token, another session's token, no token and an empty token each get the *form expired* page and change
  nothing; a post from another site gets the *not from this site* page; a cookie with no CSRF token cannot write through the
  API either.
- **Who may do what.** An anonymous visitor reads and is told proposing needs an account. A contributor proposes and
  comments, cannot review (by role) and cannot accept even by posting the accept form herself. A reviewer cannot approve or ask
  for changes on her own proposal (D9). Only the maintainer is offered, and obtains, *Accept*. Through the API: `propose`
  cannot review or accept, `review` cannot accept, a contributor's `accept` token can do neither (scope ∩ role), an invalid
  token is `invalid-token` and no cookie is looked at.
- **The flow.** Noor proposes an edit of the *Reading* paragraph of the help page; Quinn proposes another paragraph and Noor a
  second edit of the first — all three written against the same history. Noor comments; Maya approves and accepts. Then: the
  accept page says *Signed into the history*; `prikk log` has exactly one new block (the one before it is the old tip); the
  page shows the change; the proposal says *Signed into the history* and *Accepted*; the history page and the change page show
  the summary and both people; a retry of the accept writes nothing; the badge comes from a check that ran **after** the change
  (the verification page says *Verified*, *The last check found nothing wrong*, and *Last checked* the minute that check ran —
  the creation's check was aged to 1970 first, so an old time could not pass); an open proposal never changed the page every
  reader sees.
- **A moved base.** Quinn's proposal, written before Noor's was accepted, is accepted next: both changes are on the page, one
  new block (through the API the answer says `reauthored: true`).
- **An overlap.** Noor's second edit of the same paragraph stops with *Stopped: changes overlap*, the proposal says *Needs a
  revision* and shows the wiki's text and the proposal's side by side, the repository is as it was.
- **Secrets.** No password, no operator secret and no session value appears in a log, an operator note, stderr or any page any
  browser was shown.

## 7. Risks

| Risk | What it is | What bounds it | What to decide or watch |
|---|---|---|---|
| **RR-1 / RR-11 — the server holds keys** | 0.1.0's server held none. 0.2.0's reads the operator's secret file at start, decrypts a wiki's seed onto the tmpfs for the one signing call that needs it, and parses visitors' requests in the same process: a compromise of the process is a compromise of every wiki's keys (as a host compromise always was) | The signer is reached only through `Accept`; it refuses a seal not bound to a recorded acceptance; one lock with the command line; every call sandboxed under a memory ceiling, with only the seed it signs with; no second signer process (IQ-4); reconciliation reports an unrecorded seal; per-wiki keys, rotation and retirement; the process is made non-dumpable (**A1**) and warned about a secret file open to group or others (**A2**) | Say it in the release notes. SECURITY.md's operator notes say where the secret file lives and who may read it |
| **The key store appearing after the start** | A server started before the first `wiki create`, or without the secret file, serves reads and refuses every change to the history with one sentence and one operator line | By design: it never asks for the secret on a terminal | **Restart the server after the key store appears.** It is the one deployment step a new operator can miss; the refusal names the setting and says *restarted* |
| **Sessions and CSRF** | A session cookie is a bearer of the account for seven days (at most 100 live per account); every write by cookie needs the session's CSRF token, checked before the wiki is looked up | `__Host-`, `Secure`, `HttpOnly`, `SameSite=Strict`; the token in the form or the `X-CSRF-Token` header; the same-site check beside it; a token request is judged by the token alone; sign-out ends the session; signing in again ends the one presented (**G8**); a password change on the account page ends every session and every token and starts a new session for the person (**G10**, **H5**: one store step) | The server speaks plain HTTP behind the operator's TLS proxy (it refuses an `http://` origin that is not loopback, and the cookies are `Secure`): **it must sit behind TLS**. Tokens: minting asks for the password again (**G6**; for an account with no password, a sign-in of the last ten minutes) |
| **The throttle behind a proxy (G1)** | The per-address sign-in throttle counts the peer; behind a reverse proxy not declared in `INKLKUNN_TRUSTED_PROXIES`, every client is one address and thirty failed sign-ins by anyone lock everyone out. A *loopback* bind (the likely deployment: a local TLS proxy) now gets the warning too (**G1**) | The warning for any bind with no proxy declared, and one run-time line when a loopback peer sends `X-Forwarded-For` (**G1**); `X-Forwarded-For` is read from the right (**G7**) | Declare the proxy. This is the likeliest way a first deployment locks itself out |
| **A retirement that does not finish (Q1, W1 – W7)** | A retirement is two prikk steps and a record; a kill or a failure between them used to be able to strand the wiki | While a retirement is unfinished the signer **pauses every new seal** with one sentence naming the command (the proposal stays held); `inklkunn wiki keys finish-retirement <wiki>` does whatever step remains; `abandon-retirement <wiki> --confirm <slug>` puts the old key back; `keys rotate` exits non-zero naming them; nothing outside a retirement's recorded set is excused (P2′); a killed seal on a retired wiki is finished narrowly (W7) | A retired key is still a rare, deliberate act (DR-10: the label *Verified* is lost until prikk can rotate without revoking). After an abandon the old key is trusted again and is retired later by id (X1) |
| **Contributor-controlled text reaches the history** | A proposal is arbitrary Markdown by a stranger with an account | Raw HTML is escaped (IS-14), a sanitized subset renders, hostile content is data (tests), quotas refuse by name, the signer signs only a recorded acceptance of a revision a maintainer chose | The accessibility and abuse sides of a public wiki are untested by people |
| **Removal is lossy (RR-6)** | An accepted change is in an immutable history; the duty to remove content (M4) is not built | The procedure is written; no governance layer | Do not offer 0.2.0 as a host for content that may have to be erased |
| **Dependencies** | `pulldown-cmark` 0.13.6 (RUSTSEC-2026-0433, which never applied: the option is not enabled); `aws-lc-rs` in the trusted base for OpenID Connect (DR-9); prikk 0.54.0 floor | `cargo deny`, `cargo audit` re-run on the candidate (RELEASING step 2) | Re-run on the exact commit; the advisory database moves daily |
| **Per-host assumptions** | The lease and the throttles are per process (RR-7, RR-10) | One process per deployment | Do not run replicas |
