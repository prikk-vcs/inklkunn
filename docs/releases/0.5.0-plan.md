## 1. In one paragraph

**0.5.0 lets a wiki come in from elsewhere with its history, including from MediaWiki and BookStack.**
- **Most of M5 already exists.** It was built as earlier milestones needed it: the bundle export, the archive export,
  the read and write API with OpenAPI, ETags and problem details, the Atom feeds, the site description, OpenSearch,
  the sitemap and `robots.txt`.
- **What is missing is the import side.** Today `wiki import-folder` brings files in as **one change**, and it leaves
  out the history, the authors and the licences. MediaWiki and BookStack need exactly that history.
  - wiki-commons' converters already turn a MediaWiki XML dump or a BookStack ZIP into a Portable Wiki Bundle, with
    history and a report.
  - **So the core of 0.5.0 is one feature:** importing a bundle with its history.
- **The rest is small:**
  - the interwiki map, which an import needs, and which the export and the site description declare empty today;
  - the API's last conventions;
  - the conformance self-assessment;
  - making the crates publishable.
- **The scope is frozen when you authorize this plan.** A defect found during the cycle is fixed in 0.5.0. Anything
  else goes later.

**The threat model says more than the code:** C-5a says an import verifies checksums *when present*, and C-5c says it
makes *attributed changes with an import report*. Neither is true yet. 0.5.0 makes them true, or the text is
corrected.

**In 0.5.0** (RFC 007):

| | What | Requirement |
|---|---|---|
| a | **Import a bundle with its history, into a new wiki** (P-1). Each change in the bundle's history becomes a change in the new wiki, in order, attributed as the history records it. The import is still the **wiki's own signed change**, and it names the original author as data, so no one is shown as having signed what they did not. The import also: reads the fidelity level, verifies the checksums, **checks every page's and every attachment's licence against the wiki's** (a licence that is not compatible refuses the file by name), dry-runs first, and reports what it brought in and what it left out. An existing wiki keeps today's one-change folder import | IX-3, LIC-4, LIC-5, SEC-5 |
| b | **MediaWiki and BookStack, through wiki-commons' converters** (P-2). The operator runs the converter, and imports the bundle it makes. inklkunn neither embeds nor runs it. The tests use bundles the converters produced, kept in the tree with the command that made them, at a pinned wiki-commons commit | IX-3, AC-M5 |
| c | **The export carries renames and removals** as history, so that an inklkunn wiki exported and imported again keeps them | IX-1 |
| d | **The interwiki map.** A wiki's map lives in its repository, and is changed by a proposal like its rules. An import reads the bundle's map. The export's manifest and `site.json` publish it, and links resolve through it | IX-1, IX-6, IX-9 |
| e | **The API's last conventions:** a `Link: rel="next"` header beside the body's cursor; ~~rate-limit headers on the endpoints that are limited~~ (not in 0.5.0: RFC 007 Q-4, ruled 2026-11-26, since the IETF's header fields are still a draft; a refusal carries `Retry-After`); a list of a wiki's proposals; a proposal's comments to read; a proposals feed; `site.json` names the API's description | IX-4, IX-5, IX-6 |
| f | **The conformance self-assessment:** a `wiki-commons.yaml` in the tree, claiming only what a test shows (`@0.4`), and published with each release | IX-8 |
| g | **The threat model updated** for import with history (a converter's output is untrusted input; a licence or an author named in a bundle is a claim, never a fact) and for the new read endpoints | AC-M5 |
| h | **Small items, run now as one maintenance package** (P-4): **the crates become publishable** (below); and prikk 0.59.0's re-baseline, if 0.59.0 is released in the cycle (`doctor`'s new wording; the maintenance handoff's last section) | OPS-4, RFC 010 |

**The crates, found while checking whether 0.4.0 could go to crates.io:** it cannot.
- **The blocker:** four crates list themselves as dev-dependencies with a version, and the signer and the core list each
  other. Cargo keeps a dev-dependency with a version in the published manifest, so none of these can be published.
- The release workflow would have failed at the second crate, and the rehearsal never runs that step, so nothing
  showed it.
- **Also:** no crate carries the licence's text, which Apache-2.0 §4(a) asks a redistributor to give.
- **The fix:**
  - drop the version from those dev-dependencies, keeping cargo-deny green;
  - put the licence in each crate;
  - have the rehearsal run `cargo publish --workspace --dry-run`, so that this cannot pass unseen again.

  Measured on the 0.4.0 tag with only the dev-dependencies changed: all nine crates package and verify.

**Not in 0.5.0:**

| Item | Where it goes | Why it can wait |
|---|---|---|
| Replaying history into a wiki that already has pages | a later minor, if asked for | It would interleave two histories, and every conflict would need a person. A new wiki is the migration case |
| Pseudonymizing the export's contributors; a dry run and a per-namespace scope for export (IX-1) | a later minor | The export is an admin's command today. Nothing leaves the server unless the admin runs it |
| Discussions in the bundle (fidelity level 4): a proposal's comments, claim threads, view records, on export and import | with free-standing page discussion, a later minor | There is no page discussion to carry yet. The comments are the service's records, with names and hidden entries, and need their own privacy design |
| Links between the wikis of one server without a map entry | a later minor | A map entry covers it. A native link must not reveal a restricted wiki's existence, which needs its own design |
| Webhooks (IX-7) | later, by the requirement | No consumer asks for them |
| Relicensing as an event (GV-10's rest) | a later minor | A licence is read and checked in (a). Changing one is a governance act of its own |
| Free-standing page discussion, governance forks, GV-7, GV-9, attaching an existing source to another claim | later minors (as in 0.4.0's plan) | Unchanged |
| **The operations RFC:** backup and a rehearsed restore, the permanent removal procedure, IS-15's `recover`, observability, the deployment guide | **0.6.0, proposed next** | **Before any public deployment** (ROADMAP T11; 0.4.0's P-1). There are no production users (owner, 2026-11-18) |
| Native Unicode paths (prikk's format 8, from 0.57.0) | its own decision | It moves the floor from 0.54.0 and migrates every repository's format, which DUR-3 makes an operator's act |
| A second factor; a real OpenID Connect provider; an external security review; the test by a person using assistive technology | before 1.0 or the first public deployment | As recorded at 0.3.0 and 0.4.0 |

## 3. Your decisions in this plan

- **P-1 — History is imported into a new wiki only.** An existing wiki keeps today's one-change import. **Recommended.**
- **P-2 — MediaWiki and BookStack come through wiki-commons' converters,** run by the operator, not embedded. The tests
  use their output, pinned. **Recommended.**
  - The converters need Python and PyYAML, and inklkunn stays one Rust binary.
  - The converters are wiki-commons' work, maintained there.
- **P-3 — Section 2's *Not in 0.5.0* table.** **Recommended.**
- **P-4 — crates.io from 0.5.0, not 0.4.1.** The fix runs now with the small items (2h). **Recommended.**
  - No one installs from crates.io yet, so a patch release only for the crates is not worth its cost (as 0.2.1 was
    declined).
  - **One act of yours at 0.5.0's cut:** add the `CARGO_REGISTRY_TOKEN` secret to the repository. The crates are then
    published by the same run that builds and attests the binaries. Without the secret the release skips them, as
    before.
- **P-5 — 0.6.0 is the operations release** (for orientation; authorized separately). It comes before any public
  deployment.

RFC 007 brings its own design questions for your rulings. These are expected:
- **How an imported change shows its author.** The architect will recommend "imported; originally by *name*", as
  data, never as a signature.
- **What "compatible licence" means** for each of the wiki's default licences, and whether an admin may override a
  refusal.
- **What the map may contain:** prefixes, URL patterns, and which schemes.

## 4. Exit criteria (all must hold on the candidate commit)

1. **Gates green on the candidate:**
   - the architect's gates: fmt, clippy, the `+1.89.0` check, rustdoc, deny, audit, and the tests with prikk 0.55.0,
     shimmed off, on 0.57.0, and on the newest prikk asset;
   - CI;
   - the release rehearsal, **now with `cargo publish --workspace --dry-run`**;
   - the 0.54.0 floor over the whole workspace.
2. **Threat model v0.5** covers what 0.5.0 adds, and its §7 tests are re-verified on the candidate. It covers:
   - a hostile bundle (oversized, deep, links, a forged history, a forged author or licence, a checksum that lies);
   - a converter's output;
   - the interwiki map as a way to an unsafe link;
   - the new read endpoints, which must never show what moderation hides.
3. **The readiness report** is reviewed by the architect, with every RFC 007 acceptance criterion shown by a named
   test.
4. **The end-to-end proof on a real prikk:**
   - a MediaWiki dump and a BookStack export, converted by wiki-commons, come in as new wikis with their history,
     authors and licences, and their interwiki links resolve;
   - an inklkunn wiki exported and imported again keeps its pages, history, renames and removals;
   - a bundle with an incompatible licence, a bad checksum or a forged path is refused by name, and nothing is
     written.
5. **No open High issue.**
6. **An upgrade from 0.4.0 is shown.** A data directory made by the 0.4.0 release binary is opened by the candidate,
   and its wikis behave as before.
7. **The release notes' lead** says in a reader's words what 0.5.0 adds and what it does not do, with the Japanese
   statement.
8. **You review the Japanese** added or changed in the cycle, and **you authorize the cut.**
